# HOTORI 수납 화면 전체 개선 기획

대상은 수납 기록 업무다. 결제 단말기 승인·취소 연동을 이미 제공한다고 표현하지 않는다. 기존 실제 예약·그룹·원장·현금 시재·정정 이력을 유지한다.

## 화면 구조

데스크톱 기본 폭 900–1040px. 왼쪽은 객실·손님·입퇴실·요금, 오른쪽은 이번 수납과 최근 내역이다. 화면 안 중첩 세로 스크롤을 줄이고 본문 한 영역을 스크롤한다. 하단에는 판매금, 이번 수납, 등록 후 잔금, 저장을 고정한다. 좁은 화면은 동일한 순서의 한 열이다.

예약 요약 → 판매금·박별 요금 → 수단별 이번 수납 → 영업일·메모 → 합계·저장. 기존 예약에서는 요약 다음에 기수납·정정 이력을 보여준다. 단체는 단체 전체인지 특정 객실인지 항상 표시한다. 대표객실은 단체 수납의 유일한 소유자가 아니다.

## 이전과 이후 흐름

이전: 완납 선택 → 카드 선택 → 총액 입력 → 예약 생성 → 한 줄 수납 → 실패해도 창 닫기 → 별도 화면에서 내역 확인.

이후: 판매가 160,000원 확인 → 카드 140,000원·현금 20,000원 입력 → 이번 수납 160,000원·잔금 0원 검토 → 저장 → 확인된 내역 두 줄과 저장 결과 표시. 일부 수납이면 남은 금액을 그대로 보존한다. 실패하면 입력을 보존하고 같은 요청만 재시도한다.

## 단계 1 — 승인된 긴급 개선

- `shared/payment.ts`, `OnsitePayModeFields`: 단일·복합 입력, 카드/현금/이체별 금액, 합계·잔금, 정수·초과·완납 차액 검증. 자동 1/n 분할 금지.
- `data.ts`, `receiptBatch`, `useCreateReceipts`: 수납 여러 줄을 한 요청으로 저장, 제출별 고정 UUID, 기존 수납 덮어쓰기 금지, 전체 ID 재조회 검증. 예약 성공 후 수납 실패는 성공으로 닫지 않고 수납만 재시도.
- 적용: 간단 예약, 상세 신규 예약, 선택 객실 숙박 판매. 단체는 단체 소유 수납 한 번만 기록한다.
- 닫기 최소 44px(좁은 화면 48px), 증감 버튼 충돌 제거, 숙박 판매 달력 추가, 회사명 예시 제거.
- 검증: 160,000=140,000+20,000, 세 수단 조합, 선금·후불·금액미정, 일부 실패·재시도, 그룹 소유, 날짜·요금·이름 보존.

## 단계 2 — 기존 수납·퇴실 정산 입력 통합

- `PaymentDeskModal`, `CheckoutConfirmModal`, `GroupReceipt`: 같은 복합 수납 입력부를 재사용한다. 현재 원장은 여러 번 추가할 수 있으나 한 번에 복수 수단 제출은 후속 범위다.
- 기수납과 이번 수납을 분리한다. 청구액 감액·수납 정정·환불을 별도 메뉴로 두고 변경 전후 및 사유를 보여준다. 기존 RecordSheet 복원 기능을 재사용한다.
- 선택지 문구는 ‘지금 전액 수납 / 일부 수납 / 지금 받지 않음’. 상태는 기록된 실제 수납으로 계산한다. ‘잔금조정’은 ‘청구금액 정정’으로 바꿔 의미를 드러낸다.
- 검증: 기존 선금 이후 복합 잔금, 단체 공통 수납과 객실 수납 합계, 현금 시재에는 현금만 반영, 결제 실패 시 퇴실하지 않음.

## 단계 3 — 저장 신뢰성 고도화 (별도 DB 승인 필요)

현재 단계 1은 수납 행 묶음의 일괄 저장이며 예약 생성＋수납 전체가 하나의 트랜잭션은 아니다. 예약 생성 응답 자체가 끊긴 경우까지 완전한 중복 방지를 보장하지 않는다. 재시도 전 예약 목록 확인이 필요하다.

설계: 클라이언트 작업 UUID와 요청 내용을 서버에 함께 전달하고, 예약/그룹/수납을 트랜잭션 RPC에서 생성한다. 동일 작업 UUID는 동일 결과를 반환하고 다른 내용은 거절한다. RLS·호텔 소유·금액·영업일 검증 및 응답 불명 조회를 포함한다. 원장 삭제나 이전 수납 재작성은 하지 않는다. 마이그레이션 영향·롤백·권한을 별도 검토한 뒤 승인받아 진행한다.

창을 닫거나 새로고침한 뒤에도 미완료 작업을 복구하는 보관소는 이 단계에서 설계한다. 현재 긴급 개선의 재시도는 열린 화면 안에서 제공한다. 미확인 수납은 내역에서 먼저 확인한 후 재등록한다.

## 상태와 토큰

- 빈 입력: 카드 기본, 복합은 명시적으로 선택. 0원은 무수납과 구별한다.
- 계산: 판매금과 이번 수납을 독립 유지. 요금 변경 시 입력한 복합 금액을 임의 수정하지 않는다.
- 저장 중: 입력·저장·닫기 비활성, 중복 제출 차단. 오류는 관련 입력과 합계 근처에 role=alert로 표시.
- 부분 성공: 예약 저장 완료를 먼저 알리고, 요청한 수납액·수단을 고정해 재시도. 성공은 전 행 확인 후 표시.
- 키보드: dialog 이름·포커스 진입/순환/복귀, Escape, Enter 실수 제출 방지. 위험한 정정은 별도 확인.
- 타입: 제목 21–24px, 금액 20–24px, 입력 16–18px, 본문 16px, 보조 14px. 간격 4/8/12/16/24px, 주요 버튼 44px 이상.
- 색: 기존 화이트·차콜·회색 토큰, 오류/완료만 의미색. 본문 대비 4.5:1, focus와 오류는 색 외 텍스트도 사용. 애니메이션 추가 없음.

## 컷오버와 완료 판정

단계별로 기존 데이터 모델을 공유한다. 구입력과 신입력에서 별도 수납 원장을 만들지 않는다. 자동 테스트, 메모리 저장 오류 재현, FHD/774/356px 입력·닫기·달력, 예약 CRUD·정정·시재 회귀를 통과한 뒤 해당 단계의 구입력을 제거한다. 실제 운영 시험 결제 없이 검증 범위를 명시한다. 80cm 실사용 가독성과 직원 업무 시간은 현장 확인이 필요하며 측정하지 않은 값을 점수로 꾸미지 않는다.

이 문서는 전체 수정 기획이다. 이번에 구현한 단계 1과 후속 단계 2·3을 구분하며, 전체 기획을 모두 구현한 것으로 보고하지 않는다.
