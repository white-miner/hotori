# 호토리(HOTORI) 기술 설계 v2

작성일: 2026-10-17 · 상태: 구현 전 설계안

상품 정책의 기준은 [제품 기획 v2](HOTORI-제품기획-v2.md)다. 여기서 사용하는 기능 코드·명령·엔티티 이름은 HOTORI가 앞으로 구현할 내부 계약이며 이미 존재하는 SDK API를 뜻하지 않는다. 원본 v1의 개념 스키마를 확장한 것으로 실행 가능한 마이그레이션은 아직 아니다.

## 1. 지원 플랫폼

### 권장 구성

- 공통 화면: React + TypeScript 기반 반응형 웹.
- PC: 브라우저 및 설치 가능한 PWA. 초기의 PC 지원은 별도 Windows exe/macOS 앱을 뜻하지 않는다.
- Android/iOS: 공통 웹 화면을 Capacitor로 패키징한 설치형 앱. 플랫폼별 인증·파일·알림 연결부를 분리한다.
- 서버: TypeScript 기반 업무 API와 백그라운드 작업. 한 서버 애플리케이션 안에서 모듈을 나누는 구조로 시작한다.
- 저장소: PostgreSQL, 첨부 기능 도입 시 별도 비공개 객체 저장소.
- 동기화: 서버 확정 후 WebSocket 또는 이벤트 구독으로 변경 식별자를 전달하고 클라이언트가 권한에 맞는 최신 데이터를 다시 조회한다.

React의 TypeScript 지원과 Capacitor의 웹·모바일 플랫폼 지원은 공식 문서로 확인했다. 웹·PWA를 만들었다는 이유로 Android/iOS 앱 출시가 완료되는 것은 아니다. 각 앱의 빌드·서명·배포·실기기 검수·스토어 심사를 별도 완료해야 한다. iOS 빌드는 Mac 또는 macOS 기반 빌드 환경과 Xcode를 확보한다. 현재 작업 PC는 Windows이므로 이 환경 확보가 iOS 출시의 선행 조건이다.

근거: [React TypeScript](https://react.dev/learn/typescript), [Capacitor 설치](https://capacitorjs.com/docs/getting-started), [환경 설정](https://capacitorjs.com/docs/getting-started/environment-setup), [Web/PWA](https://capacitorjs.com/docs/web).

### 플랫폼 어댑터 경계

인증 토큰 보관, 딥링크, 파일 저장·공유, 푸시 알림, 스토어 구독은 플랫폼별 연결부에서 처리한다. 재고·금액·권한·예약 기간은 서버 규칙을 공유한다. 앱에 결제 비밀키나 호텔 전체 접근용 자격 증명을 포함하지 않는다. 지원 최소 OS/브라우저 버전은 선택한 안정 버전의 호환성과 파일럿 기기를 확인한 뒤 고정한다.

PC 키보드/마우스, Android 뒤로가기·키보드, iOS 안전 영역·키보드·재로그인·복귀 흐름을 각각 검수한다. PWA는 즉시 갱신 가능하지만 설치형 앱은 업데이트가 늦을 수 있으므로 서버 계약 버전과 이전 앱 호환 범위를 관리한다.

## 2. 확장 가능한 구조

공통 UI → 인증된 업무 API → 예약·객실·매출·팀·구독 모듈 → PostgreSQL의 구조다. 백그라운드 작업과 실시간 알림도 같은 업무 명령과 권한 검사를 거친다.

### 모듈

- identity/tenancy: 계정, 조직, 호텔 소속, 세션, 역할·작업 권한.
- property: 호텔, 동, 객실 타입, 실물 객실, 가동·보관 상태.
- reservation/inventory: 예약, 숙박 단위, 날짜별 재고, 배정, 입퇴실, 취소.
- operations: 청소·시설 상태, 객실 문제, 인수인계, 판매 중지.
- finance: 판매·수수료 스냅샷, 추가요금, 입금·환불, 정산, 보고서.
- team/attendance: 조직 구성원, 근무 세션, 정정 요청과 승인.
- billing/entitlements: 플랜 버전, 호텔 구독, 결제 제공자 연결, 기능·한도 판정.
- audit/import/export: 변경 이력, 파일 이전, 원본 출력, 복구·관측 기능.

처음부터 모듈별 별도 서버, 플러그인 마켓, 임의 스크립트 실행기를 만들지 않는다. 예약·금액·권한의 경계를 먼저 안정화한다. 이후 모듈을 분리할 필요가 생기면 명령과 이벤트 계약을 유지하며 옮긴다.

새 기능은 기능 코드, 권한, 입력·출력 계약, 데이터 마이그레이션, 무료/유료 정책, 사용량 기준, 관련 화면, 검수 사례, 배포 토글을 함께 추가해야 완료다.

## 3. 구독 권한과 직원 권한

허용 조건은 `호텔 소속 유효 AND 작업 권한 보유 AND 필요한 구독 기능 보유 AND 사용량 한도 충족`이다. 구독 권한이 있다고 직원이 매출·출퇴근 기록 전체를 볼 수 있는 것은 아니다. 배포 토글과 호텔의 기능 사용 설정도 별도로 적용한다.

### 내부 정책 키 초안

- `reservation.future_months`: 무료 1 / 프로 6. 사용자 확인 완료.
- `reservation.history_months`: 무료 1 / 프로 6. 사용자 확인 완료. 미래 기간과 별도 키로 관리.
- `reports.period`: 무료 false / 프로 true.
- `rooms.max_registered`: 무료 20 / 프로 null. null은 상품상 제한 없음이며 0이 아니다.
- `buildings.max_registered`: 무료 1 / 프로 null. 무료 값은 제안.
- `room_issues.max_open_per_room`: 무료 1 / 프로 30. 객실별 미해결 기준, 사용자 확인 완료.
- `members.manage`: 두 플랜 true. 인원별 유료 과금은 초기 상품에 없음.
- `attendance.track`: 무료 false / 프로 true.
- `data.raw_export`, `audit.basic`, `rooms.basic_status`: 두 플랜 true.

`reports.history_months`는 무료 1 / 프로 6을 제안한다. 예약 제한에서 자동 상속하지 않고 독립 정책으로 둔다. 근태 이력 조회에도 예약 기간 키를 재사용하지 않는다. 근태·객실 문제의 보관 기간과 예약 조회 기간은 별도다.

`plan_versions`에 기능 정책과 가격 조건을 버전별로 고정한다. 정책 키마다 타입과 검증 규칙을 정의하며 임의 JSON 입력을 그대로 권한으로 실행하지 않는다. 플랜 이름이 `pro`인지만 비교하는 조건을 모든 화면에 흩뿌리지 않는다.

### 판정 순서

1. 인증과 호텔 소속을 확인한다. 요청의 property_id를 그대로 신뢰하지 않는다.
2. 작업 권한을 확인한다. 조회 응답의 민감 필드도 권한에 따라 선택한다.
3. 서버가 현재 호텔 구독·유효기간과 플랜 버전을 읽는다.
4. 기능, 기간, 사용량 및 기존 예약 보호 예외를 검사한다.
5. 예약/등록 같은 변경은 사용량·재고 검사와 저장을 같은 트랜잭션에서 확정한다.
6. 감사 이력과 발행할 이벤트를 같이 기록한 뒤 커밋한다.

구독 변경도 같은 호텔의 정책 잠금 규칙을 따른다. 권한 만료·무료 전환과 동시에 예약 요청이 들어와도 하나의 순서로 처리한다. 캐시된 화면 권한은 안내용이며 서버의 유효기간 검사를 대체하지 않는다.

### 과거 조회 기간 제한

일반 예약 조회는 호텔 현지 오늘 D와 `history_months`로 과거 하한 L을 구한다. 숙박일이 `[L, H)`에 속하는 데이터만 검색·달력·예약 상세·검색 건수·합계·감사 이력·일반 출력에 반환한다. 접수일을 바꿔 과거 숙박 기록을 최근 기록으로 위장할 수 없다.

경계에 걸친 연박은 허용 날짜의 night와 필요한 예약 식별 정보만 반환하는 조회 모델을 둔다. 헤더 총금액·원문 감사 로그·검색 제안·파일을 통해 기간 밖 요금과 기록이 새지 않도록 한다. 현재 투숙·미처리 금융 업무는 명시적인 업무별 조회 계약으로 필요한 범위만 제공한다. 단순 ID 직접 조회는 예외가 아니다.

무료 전환 전 확정한 미래 예약에는 보호 대상임을 식별할 수 있는 생성 시점·권한 버전을 남긴다. 기존 예약 보호를 판정할 때 클라이언트 플래그를 믿지 않는다. 기간 제한은 삭제 작업이나 백업 보존 기간이 아니며 기간 밖 데이터 반환·탈퇴 절차는 별도 정책이다.

### 직원 역할 기본안

- 소유자: 호텔 소유권·구독·전체 설정·권한 관리. 마지막 소유자 제거를 금지한다.
- 관리자: 예약·객실·정산·팀 업무. 소유권과 결제 권한은 별도 부여한다.
- 프런트: 예약·배정·입퇴실·결제 기록. 환불·소급 변경·매출 보고서는 지정 권한 필요.
- 객실관리: 담당 객실의 청소·시설·인수인계. 기본적으로 고객 연락처·매출은 조회하지 않는다.
- 출퇴근 이용자는 자기 기록만 본다. 근태 승인·타인 조회는 별도 권한이다.

이름보다 작업별 권한을 기준으로 한다. 역할 변경·탈퇴 후 기존 실시간 구독과 백그라운드 다운로드 링크도 무효화하거나 재검증한다.

## 4. 데이터 모델

모든 호텔 업무 엔티티에 property_id를 명시하고, 호텔이 다른 상위 엔티티를 참조하지 못하도록 `(property_id, id)` 복합 키와 외래키를 설계한다. 조직은 묶음과 소유 관계, 호텔은 운영·재고·구독·접근의 기준이다.

### 소속과 공간

- organizations: 운영 조직.
- properties: 호텔, organization_id, 시간대, 통화, 운영 설정.
- buildings: property_id, 동 이름, 보관 여부. 기본 동도 실제 레코드로 생성한다.
- room_types: property_id, 타입 이름. 타입은 여러 동에 걸칠 수 있다.
- rooms: property_id, building_id, room_type_id, room_number, 층, 가동 기간, 보관 상태.
- users / property_members / roles / permissions: 계정, 호텔 소속, 작업 권한. 인증 자격은 검증된 인증 계층에서 관리한다.

동을 지정한 타입 재고는 해당 동 객실만 계산한다. 동 미지정 판매는 호텔 전체 해당 타입을 계산한다. 초기 예약은 동 미지정 판매와 후속 실물 배정을 기본으로 하고, 동 지정 판매를 제공할 경우 그 제약을 숙박 단위에 저장한다. 다른 동으로 임의 배정하지 않는다.

### 예약의 수량 모호성 제거

v1의 `reservation_items.quantity`만으로는 2실 중 1실 취소, 객실별 이동, 서로 다른 가격을 정확히 연결하기 어렵다. v2는 **한 객실에 해당하는 논리적 숙박 단위**를 만든다.

- reservations: 예약 헤더, 채널, 외부 예약번호, 최소 고객 정보, 상태, version.
- reservation_stays: 헤더 아래 객실 1개 분량의 숙박 단위. 2실 예약은 2개 stay를 생성한다.
- stay_segments: stay의 타입·날짜 구간. 타입 변경·객실 이동을 위해 시간 구간을 분할한다. 같은 stay 안의 점유 구간 중복 금지.
- reservation_nights: `(stay_id, stay_date)`별 객실박 1개와 해당 날짜 금액, 활성/취소 상태. 부분 취소는 해당 stay·날짜에 연결한다.
- room_assignments: stay/segment의 실물 객실과 배정 구간. 객실번호 지정은 필수가 아니다.
- room_blocks: 실물 객실의 판매 중지 구간, 이유, 처리 상태와 작성자.
- inventory_day_locks: `(property_id, room_type_id, stay_date)`별 잠금 대상. 예약이 0건인 날에도 잠글 행이 존재해야 한다.

예: 디럭스 2실 × 2박은 reservation 1개, stay 2개, 활성 night 4개다. 1실의 두 번째 밤만 취소하면 활성 night는 3개가 된다. 객실 배정을 추가한다고 예약 수량을 또 차감하지 않는다.

### 객실 업무

- room_operational_state: 청소·시설 상태와 version. 현재 점유는 배정·입퇴실 정보에서 산출한다.
- room_issues: 객실별 인수인계 항목과 해결 상태.
- room_issue_events: 접수·수정·담당 변경·해결·재열기 이력. 사진은 후속 도입.

예약 상태, 점유, 청소, 시설을 하나의 enum으로 합치지 않는다. ‘청소 필요’는 미래 모든 날짜에 대한 영구 판매 중지와 다르다. 미래 객실 배정은 준비 상태를 안내하고, 실제 체크인은 준비 완료·시설 정상 여부를 강제 검증한다.

### 금액과 근무

- channels / channel_fee_rules: 판매 경로와 유효일별 수수료 규칙.
- reservation_fee_snapshots: 예약 시 적용한 기준·요율·반올림·버전과 산출 결과.
- reservation_charges: 추가요금·할인·위약금. 발생 사유와 귀속일을 보존한다.
- guest_payment_transactions: 호텔 고객의 수납·환불, 원거래 연결, 외부 참조.
- settlements / settlement_allocations: 플랫폼 입금과 여러 예약 간 배분. 한 입금이 여러 예약에 대응하는 경우 지원.
- attendance_sessions: 출근·퇴근 UTC 시각, 직원, 호텔, 상태.
- attendance_adjustments: 수정 요청, 이전/이후 시각, 이유, 승인자.

호텔 고객 숙박비 기록과 HOTORI 프로 구독 결제 기록은 테이블·권한·화면을 분리한다.

### 상품·구독·공통 운영

- plans / plan_versions: 상품, 버전별 정책·가격. 판매 가격 변경 시 과거 구독의 계약 버전 보존.
- property_subscriptions: 호텔, 제공자, 구독 식별자, 상태, 이용기간, 갱신 취소 예약.
- subscription_events: 수신 이벤트 식별자, 수신·처리 상태, 제공자 확인 결과. 비밀 결제정보 최소화.
- property_license_rooms: 무료 전환 후 판매 대상으로 선택한 객실과 적용 이력.
- audit_logs: 수행자, 호텔, 작업, 대상, 최소 변경 정보, 시각. 비밀번호·토큰·불필요한 고객 원문 저장 금지.
- idempotency_requests: 호텔·수행자·명령·키·요청 해시·결과.
- outbox_events: 커밋 후 발행할 변경 이벤트와 재시도 상태.
- import_batches / import_rows / export_jobs: 검토·승인·오류·처리 결과와 소유 범위.

이것은 논리 모델이다. 모든 후속 모듈 테이블을 첫날 생성하지 않고 각 개발 단계의 실제 범위에 맞춰 마이그레이션한다.

## 5. 재고와 무료 전환

### 기본 재고

숙박 날짜는 호텔 시간대의 date, 이벤트 시각은 UTC instant로 저장한다. 숙박 점유는 `[check_in, check_out)`다. 예약 접수 시각이나 영업일 마감시간을 숙박일 계산에 혼용하지 않는다.

타입·숙박일별 기본 잔여량은 가동 객실 수에서 판매 중지 객실 수와 유효 예약 객실박 수를 차감한다. 예약과 실물 배정은 같은 점유를 가리키므로 두 번 차감하지 않는다. 같은 객실의 겹치는 판매 중지 기간도 합집합으로 1실만 차감한다.

계획된 판매 중지·객실 축소도 예약과 같은 재고 잠금을 얻고 기존 예약 충돌을 검사한다. 충돌 시 무조건 저장 성공시키지 않는다. 실제 긴급 고장은 기록을 막지 않고 **재배정 필요/수용 부족 예외 상태**로 남기며 해당 범위의 신규 예약을 차단한다. 예약은 자동 삭제하지 않는다. 판매 가능 0과 기존 예약 수용 부족 수를 따로 표시한다.

v1의 ‘예약과 겹치는 판매 중지 차감 제외’만으로 처리하면 실제 수용 능력 부족을 숨길 수 있다. v2에서는 예약 의무를 유지한 채 대체 객실 확보 필요를 추적한다. 긴급 충돌이 해결되기 전에는 낙관적인 잔여 수량을 표시하지 않는다.

### 한 거래에서 예약 확정

1. 권한·구독·기간과 요청 키를 검증한다.
2. 영향을 받는 호텔·타입·날짜 잠금 행을 확보한다. 없는 행은 유일 키로 안전하게 만든다.
3. 잠금은 정해진 타입·날짜 순서로 얻고 **잠금 획득 후** 현재 재고를 다시 읽는다.
4. 기존 점유 해제와 신규 점유 확보를 같은 거래에 적용한다.
5. 숙박일·요금·감사 로그·outbox를 함께 저장하고 커밋한다.
6. 실패하면 기존 예약과 재고를 그대로 유지한다. 충돌·재시도 이유를 구체적으로 반환한다.

예약뿐 아니라 취소·부분 취소·타입 변경·판매 중지·가동 객실 변경·라이선스 객실 선택이 같은 잠금 규칙을 지킨다. 멱등성 키를 같은 내용으로 재전송하면 같은 결과를 돌려주며, 키를 다른 내용으로 재사용하면 충돌을 반환한다. 오래 열린 화면 수정은 version을 비교해 충돌을 안내한다.

실제 구현은 PostgreSQL 행 잠금과 제약을 조합한다. 예약이 없는 날의 예약 행만 `FOR UPDATE`하는 방식은 빈 집합을 잠그지 못하므로 사용하지 않는다. 잠금·교착상태·정해진 순서의 근거는 [PostgreSQL Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html)에 있다.

### 객실 배정과 연박

배정과 판매 중지는 실물 객실에 대해 공통 잠금을 얻어 겹침을 검사한다. 배정 테이블의 기간 겹침은 date range와 exclusion constraint 등으로 방어하고, 판매 중지와의 교차 충돌은 같은 서버 명령 경계에서 검사한다. 두 테이블에 각자 겹침 제약을 두는 것만으로 테이블 간 충돌까지 방지했다고 간주하지 않는다.

연박은 날짜별 수량뿐 아니라 연속 객실 배정 가능성을 확인한다. 이동 없이 배정 불가하면 이동이 필요한 예약임을 표시하고 승인한 뒤 저장한다. 방 이동·타입 변경은 구간을 나눠 원래 이력을 유지한다.

근거: [PostgreSQL Range Types](https://www.postgresql.org/docs/current/rangetypes.html), [Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html). 여러 행의 합계 한도는 단순 CHECK 제약으로 보장할 수 없으므로 서버 거래와 잠금을 사용한다.

### 무료 전환 시 이중 재고 제한

전체 객실(T)과 무료 신규 판매 대상으로 선택한 최대 20실(S)을 구분한다. 기존 예약은 T에서 이행하고, 무료 신규 예약은 S에서 이행할 수 있어야 한다. 기존 예약을 집계에서 빼고 S만 빈 방으로 계산하면 중복 판매가 발생한다.

구현 계약:

- 모든 신규 무료 예약에 S의 객실만 배정 가능하다는 범위를 기록한다.
- 전환 전 예약은 기존 배정 및 동 제약을 보존하되, 허용 범위에서 T로 재배정 가능하다.
- 고정된 배정은 해당 실물 객실을 먼저 점유한다. 미배정 무료 예약은 S의 잔여 수량을 예약하고, 미배정 기존 예약은 자신의 허용 범위를 점유한다.
- 날짜별로 S의 수용량과 T의 전체 수용량을 모두 만족해야 한다. 기존 예약의 모든 타입·동·날짜 제약을 계산에 포함한다.
- 제약이 다른 미배정 예약이 혼재하면 단순 `min(전체 잔여, 선택 객실 수)`가 아니라 허용 객실 집합을 고려한 배정 가능성 검사로 판단한다. 수용 가능한 배정이 없으면 신규 확정하지 않는다.
- 여러 날짜가 필요한 경우 같은 객실 연속 배정/승인된 이동 구간도 확인한다.
- 첫 구현은 이 복잡성을 숨기지 않도록 기존 미배정 예약을 판매 객실 선택 과정에서 배정하거나, 해당 타입·날짜의 신규 무료 판매를 보류하고 담당자에게 정리를 안내하는 보수적 경로를 허용한다. 기존 입퇴실은 막지 않는다.

20실 초과 상태에서 S의 선택이 끝나지 않으면 신규 무료 판매만 보류한다. 라이선스 객실 선택을 바꾸는 경우 이미 받은 무료 예약의 수용 가능성을 같은 거래에서 확인한다. 매번 선택을 바꿔 20실 초과를 동시에 신규 판매하는 우회가 가능하면 안 된다.

## 6. 매출·수수료·시간 계산

- KRW 금액은 정수로 저장한다. 요율은 정확한 소수/정수 비율로 계산하고 반올림 위치를 명시한다.
- 숙박 단위·숙박일별 금액을 저장한다. 총액을 균등 분배할 때 생기는 원 단위 나머지는 정해진 날짜 순서로 배분하고 합계가 원총액과 같아야 한다. 사용자가 일별 요금을 지정하면 그 값을 우선한다.
- 건당 고정 수수료는 예약당 한 번 적용한다. 2실×2박을 4번의 예약으로 계산하지 않는다.
- 수수료 규칙과 입력 기준·결과를 예약 시 스냅샷으로 보존한다. 설정 변경이 과거 예약 금액을 조용히 바꾸면 안 된다.
- 매출(숙박일), 접수 실적(예약 접수일), 현금흐름(입출금일)은 별도 질의다. 세금 신고용 회계 기능을 완성한 것으로 표시하지 않는다.
- 노쇼는 관리자 확정 시 실제 제공하지 않은 숙박 매출과 취소/위약금을 구분하고, 남은 날짜 재고의 해제 시점을 기록한다. 상태명만 바꾸고 자동으로 모든 재고를 소급 해제하지 않는다.
- 무료의 단일 날짜 리포트와 프로의 다일 집계는 서버에서 구분한다. 제안한 보고서 과거 범위를 별도 검사한다. 원본 내보내기도 호텔 격리·권한·예약 조회 범위를 검사하며, 파일 작업 생성 후 무료 전환되면 다운로드 때 권한을 다시 확인한다.
- 호텔 영업일 마감시간은 현금 마감 등 해당 보고서에만 명시적으로 적용한다. 변경은 과거 집계 기준과 버전을 남긴다.
- 출퇴근은 서버 시각을 사용하고 UTC 차이로 근무 시간을 구한다. 직원별 열린 근무 세션을 중복 생성하지 못하도록 유일 제약/잠금을 둔다. 자정 기준으로 강제 퇴근시키지 않는다.

## 7. 구독과 결제 제공자

초기 기반에는 테스트용 호텔 구독 상태를 만들되 실제 고객 결제와 분리한다. 실결제 제공자는 정하지 않았으므로 Stripe·국내 PG·StoreKit·Play Billing을 이미 채택했다고 가정하지 않는다.

모든 제공자 연결부는 검증된 외부 구독을 내부 호텔 구독으로 변환한다. 웹 결제 알림의 서명 검증 또는 제공자 조회, 앱스토어 구매 검증, 이용기간 확인이 완료되어야 권한을 부여한다. 비검증 이벤트는 구독 상태를 바꾸지 않는다.

결제 화면 복귀, 웹훅, 스토어 알림은 중복·지연·역순으로 도착할 수 있다. 외부 이벤트의 유일 식별자로 멱등 처리하고 최신 제공자 상태와 대조한다. 오래된 성공 이벤트가 환불·만료 상태를 덮어쓰지 않도록 한다. 정기 대조 작업으로 누락 이벤트를 복구한다.

내부 상태는 무료, 결제 확인 중, 유료 유효, 만료/무료 전환, 결제 실패 확인 등으로 명시한다. ‘갱신 중지 예약’은 유효기간 내 이용권과 별개다. 구체적인 제공자 상태 매핑·유예·환불 처리·즉시 권한 종료 시점은 제공자 선정 후 계약 테스트로 확정한다.

하나의 호텔에 여러 기기에서 결제를 시도하면 기존 구독을 먼저 확인한다. 동일 호텔의 웹/Android/iOS 이중 구독을 기본 경로에서 막고, 복원된 구매는 원래 호텔 소속과 연결을 서버가 검증한다. 임의로 다른 호텔의 구독으로 옮길 수 없다. 기존 구독이 있는데 다른 결제 경로로 이동할 때는 겹치는 이용기간과 해지를 안내한다.

### 앱스토어 정책에 따른 출시 조건

- 호텔 투숙객의 숙박비와 호텔 운영자가 지불하는 HOTORI 소프트웨어 구독료는 서로 다른 거래다.
- Apple의 조직 대상 서비스 예외는 실제 판매 대상과 직원 사용 모델에 조건이 있다. 호텔당 과금이라고 자동 적용하지 않는다. 일반 디지털 구독에는 앱 내 구매 요건을 검토한다.
- Apple의 일부 무료 companion 앱 예외를 호텔 PMS 전체에 적용할 근거로 삼지 않는다. 단순 웹 포장 앱의 기능성 심사도 고려한다.
- Google의 기존 외부 구매 서비스에 로그인하는 consumption-only 방식과 앱 안에서 구독을 판매하는 방식은 구분한다. 외부 구매 유도와 지역별 프로그램은 채택 시 다시 확인한다.
- 플랫폼별로 구매 UI가 다르더라도 검증된 호텔 이용권의 업무 기능은 공통 적용한다. 가격 표시·복원·해지 안내는 선택한 판매 모델에 맞춘다.

2026-10-17 확인 근거: [Apple 심사 지침 3.1.3·4.2](https://developer.apple.com/app-store/review/guidelines/), [Google 결제 정책](https://support.google.com/googleplay/android-developer/answer/9858738?hl=en), [Google 정책 FAQ](https://support.google.com/googleplay/android-developer/answer/10281818?hl=en). 정책·지역·실제 심사 결과에 따라 달라지므로 최종 출시 시 재검증한다.

## 8. 격리·보안·오프라인·운영

### 호텔 격리

호텔별 필터를 화면에만 적용하지 않는다. API, DB 연결 컨텍스트, 복합 외래키, 실시간 채널, 파일 작업, 백그라운드 작업에 호텔 소속을 적용한다. PostgreSQL RLS를 방어 계층으로 사용할 경우 애플리케이션 DB 역할의 우회 권한·소유자 동작을 고려한다. 연결 풀에 이전 요청의 호텔 컨텍스트가 남지 않도록 거래 단위로 설정한다.

근거: [PostgreSQL Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html). 테스트는 반드시 실제 앱 역할로 하고 관리자 DB 계정으로만 통과했다고 격리를 보장하지 않는다.

### 실시간과 연결 끊김

커밋 전에 성공 이벤트를 보내지 않는다. 커밋과 outbox를 함께 저장하고 발행 실패 시 재시도한다. 이벤트는 중복 수신 가능하므로 버전·식별자를 사용한다. 재접속 시 최신 상태를 다시 읽고, 로그아웃·소속 변경 시 개인 캐시와 구독 연결을 제거한다.

오프라인에서는 캐시된 최소 조회 정보와 마지막 갱신 시각만 표시한다. 고객 정보·매출을 무조건 기기에 영구 캐시하지 않는다. 미전송 초안은 확정 예약과 다르게 표시하고, 인터넷 복구 후 현재 권한·기간·재고로 다시 검증한다. 오프라인 신규 예약·출근을 서버 확정으로 표시하지 않는다.

### 파일 이전과 출력

CSV 표준 양식 → 열 매핑 → 미리보기 → 오류/중복 확인 → 명시 승인 → 업무 명령으로 저장 → 행별 결과 제공. 모든 엑셀 양식 자동 인식은 약속하지 않는다. 가져오기도 유료 기간·객실 수·권한·재고 검증을 우회하지 못한다.

대량 작업은 청크 단위의 원자성과 실패 행을 표시하고, 전체 파일이 전부 저장됐다고 잘못 안내하지 않는다. 재시도 시 이미 저장한 행을 중복 생성하지 않는다. 출력은 작업 소유 호텔과 요청자 권한을 다운로드 시점에도 검사하며 만료 링크를 사용한다. 스프레드시트 수식 주입을 고려해 문자열 출력 규칙을 적용한다.

### 운영 기본선

TLS, 안전한 세션·기기 자격 보관, 요청 제한, 비밀정보의 서버 관리, 비공개 첨부, 최소 로그, 데이터 보존·파기, 오류 추적, 자동 백업과 별도 복구 리허설을 운영 투입 전에 갖춘다. 상품상 ‘무제한’과 기술적 페이지 크기·파일 크기·동시 요청 제한을 구분한다.

호텔 원본 데이터/근태 기록을 모델 학습이나 외부 서비스에 임의 전송하는 기능은 만들지 않는다. 복구 목표 시간·허용 손실 범위와 실제 인프라 비용은 호스팅 선정 후 파일럿 전에 정한다.
