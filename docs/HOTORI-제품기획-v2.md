# 호토리(HOTORI) 제품 기획 v2

작성일: 2026-10-17 · 상태: 개발 기준안, 일부 상품 정책은 제안

## 제품 이름과 브랜드 방향

프로젝트의 공식 이름은 **호토리**, 영문 표기는 **HOTORI**, 개발 식별자는 `hotori`다. 이전 가칭 ROOMFLOW를 대체한다.

브랜드 표현은 **ホテル トータル レポート**이며, 제품 소개는 **호텔 토탈 리포트 · 곁에 있는 운영 파트너**로 정리한다. 사용자가 제시한 `ほとり`의 ‘곁, 주변’ 이미지를 바탕으로, 복잡한 업무를 기억하고 운영자 곁에서 예약·객실·판매금·인수인계를 연결하는 제품을 지향한다.

“호토리에 예약 기록해 줘.”는 이름을 사용하는 예시다. 음성 인식·AI 자동 등록 기능을 현재 개발 범위에 추가하는 요구로 간주하지 않는다.

## 1. 제품이 해결할 문제

프런트 직원이 예약을 입력하면 판매 가능한 객실이 정확히 바뀌고, 다른 직원이 PC와 휴대폰에서 같은 정보를 확인하며, 관리자는 판매금액과 객실 문제를 추적할 수 있게 한다.

주요 문제는 예약·취소의 중복 입력, 객실 수량 오계산, 판매금액과 정산액의 혼동, 객실 고장과 수리 내용의 인수인계 누락이다. 첫 검증 현장은 사용자가 근무하는 호텔이다. 고객 범위는 소규모 숙박업소에서 시작하되 객실·동·직원 수가 늘어도 구조를 바꾸지 않는다.

외부 숙박 플랫폼의 예약·취소·재고 API는 최초 제품에 연결하지 않는다. 직접 입력하거나 사용자가 검토·승인한 파일만 반영한다. 자체 서버 API, 실시간 통신, 구독 결제 연동은 사용할 수 있다. 외부 플랫폼의 재고 일치는 자동 보장하지 않는다.

## 2. 확정 요청과 제안의 구분

### 사용자가 제시한 상품 기준

- PC, Android, iOS 모두 지원한다.
- 기능을 계속 확장할 수 있어야 한다.
- 무료: 객실 예약관리 1개월, 객실 일일 판매금 확인, 객실 상태 기록 1개, 객실 등록 20개, 호텔 조직 구성원 등록.
- 프로: 월 30,000원, 객실 예약관리 6개월, 기간별 판매금 확인, 객실 상태 기록 30개, 객실·건물동 등록 제한 없음, 조직 구성원 등록과 출퇴근관리 기록.
- 실무에 필요한 추가 기능을 순차 개발하고 무료·유료로 구분한다.

### 이 기획에서 제안한 운영 기준

- 프로는 기능마다 30,000원을 내는 방식이 아니라 **열거한 프로 기능을 포함하는 하나의 월 구독**이다.
- 과금 단위는 **호텔 1곳(property)**이다. 직원 개인이나 접속 기기마다 추가 결제하지 않는다. 여러 동이 같은 호텔에 속하면 같은 구독을 적용한다.
- 여러 호텔을 가진 조직은 호텔별로 구독한다. 여러 사업장 묶음 요금은 후속 상품이다.
- 무료는 기본 동 1개를 제공한다. 프로는 여러 동을 관리한다. 무료의 동 수는 사용자 예시에 없으므로 제안이다.
- 구성원 등록은 두 플랜 모두 제공하며 현재 상품상 인원 제한은 두지 않는다. 초대·권한·접근 철회도 기본 제공한다.
- 가격의 세금 포함 여부, 결제 경로, 무료 체험, 연간 결제, 환불·일할 계산은 아직 결정하지 않았다. 유료 출시 전에 확정한다.

### 사용자 답변으로 확정한 두 항목

1. 예약 1개월/6개월: **과거 예약 조회 기간과 미래 예약 관리 기간 모두 제한**한다. 무료는 과거 1개월·미래 1개월, 프로는 과거 6개월·미래 6개월이다.
2. 객실 기록 1개/30개: **객실별 동시에 열려 있는 미해결 인수인계 항목 수**다. 평생 누적 기록 수가 아니다.

이는 2026-10-17 추가 답변으로 확인했다. 조회 가능 기간과 데이터 보관 기간은 구분한다. 나머지 세부 운영 규칙은 아래의 제안 기준을 따른다.

## 3. 무료와 프로의 기능 계약

### 3.1 예약관리

무료는 과거 조회 1개월·미래 예약 1개월, 프로는 과거 조회 6개월·미래 예약 6개월을 제공한다. 예약 건수는 별도 상품 제한을 두지 않는다. 기간은 고정 30일/180일이 아니라 호텔 현지 날짜에 달력상의 월을 더하거나 빼서 계산한다.

제안 규칙: 오늘을 D, 플랜의 허용 개월 수를 N, 과거 하한을 L = addCalendarMonths(D, -N), 미래 상한을 H = addCalendarMonths(D, N)으로 한다. 일반 조회 대상 숙박일은 `[L, H)`다. 신규 미래 예약의 모든 숙박일은 `[D, H)` 안에 있어야 한다. 체크아웃은 H까지 허용한다. 월말에 없는 날짜는 해당 월의 마지막 날로 보정한다.

예: 호텔 기준 2026-10-17이라면 무료의 과거 조회 하한은 9월 17일, 마지막 신규 허용 숙박일은 11월 16일, 체크아웃은 11월 17일까지다. 프로의 과거 조회 하한은 4월 17일이며, 신규 예약은 2027년 4월 16일 숙박, 4월 17일 체크아웃까지다. 2027-01-31에서 1개월 상한은 2월 28일이다.

- 예약 등록·변경·취소, 부분 취소, 체크인·체크아웃, 객실 배정은 두 플랜 모두 제공한다.
- 과거 예약 검색·상세·연결 이력은 각 플랜의 조회 기간 안에서 제공한다. 기준은 예약 접수일이 아니라 숙박일이다. 기간과 겹치는 연박은 예약의 문맥을 유지하되 범위 밖 금액·이력을 일반 조회로 풀어 주지 않는다. 현재 투숙·미처리 업무 예외는 7절을 따른다.
- 과거 입력·수정은 조회 기간, 작업 권한과 마감 규칙을 모두 검사한다. 예약번호 직접 입력, 검색, 복사, 달력, API, 일반 내보내기도 동일한 조회 제한을 지킨다.
- 기간 밖 데이터는 자동 삭제하지 않는다. 예약 기간 제한을 다른 모듈에 무조건 재사용하지 않고 데이터 유형별 정책을 둔다.
- 허용 기간 밖을 일부 포함한 신규 예약은 전체를 거절하고 가능한 날짜를 안내한다. 자동으로 날짜를 잘라 저장하지 않는다.
- 업그레이드 전에는 실제 결제·권한 확정 없이 6개월 예약을 저장하지 않는다.
- CSV 가져오기, 복사 예약, 일괄 등록에도 같은 규칙을 적용한다.
- 구독 종료 전에 받은 예약과 과거 미처리 건의 처리는 7절의 기존 업무 보호 규칙을 따른다.

### 3.2 매출·정산

무료는 선택한 하루의 객실 판매금액, 수수료, 예상 정산액, 실제 입금액과 해당 거래 상세를 제공한다. 프로는 주·월·사용자 지정 기간의 집계, 추이, 객실 타입·채널별 비교, 집계 보고서 출력을 제공한다.

추가 제안: 1차 리포트의 과거 날짜 범위도 무료 1개월·프로 6개월에 맞춘다. 이는 사용자가 직접 지정한 매출 기간 제한이 아니라 예약 조회 제한과의 일관성을 위한 제안이다. 1년 전체 분석은 현재 프로에 포함됐다고 약속하지 않는다. 장기 통계와 보존 기간은 별도 정책으로 확장할 수 있다.

- 기본 매출은 숙박일 기준 객실 매출이다. 예약 접수일 판매 실적, 실제 입금일 현금흐름을 구분한다.
- 객실 판매금액, 수수료, 예상 정산액, 실제 입금액은 별도 수치다. 예상 정산액을 순이익으로 표시하지 않는다.
- 취소 위약금과 추가요금은 객실 숙박 매출과 구분한다. 환불은 원거래에 연결해 별도 기록한다.
- 앱 안의 원본 예약·결제·이력 내보내기는 두 플랜 모두 해당 조회 범위에서 제공한다. 기간 집계 보고서가 프로 기능이다. 범위 밖 데이터의 반환·탈퇴 절차는 별도로 정한다.
- 무료 사용자가 일별 자료를 직접 합산하는 것까지 막지 않는다. 프로의 가치는 자동 집계와 비교·추이 분석이다.

### 3.3 객실 상태와 인수인계

기본 객실 상태(공실·투숙, 청소 필요·중·완료, 정상·점검·판매 중지)는 두 플랜 모두 제공한다. 고장 표시와 판매 중지 처리를 유료 기능으로 막지 않는다.

추가로 작성하는 구조화된 인수인계 항목은 객실별 미해결 기준 무료 1개, 프로 30개다. 항목에는 제목, 유형(고장/컨디션/수리/기타), 내용, 중요도, 담당자, 상태, 작성자·시간, 처리자·시간을 기록한다.

- 상태: 접수 → 처리 중 → 해결. 해결 항목을 다시 열 수 있으나 미해결 수 제한을 재검사한다.
- 사진 첨부, 기한 알림, 점검 체크리스트는 후속 프로 후보다. 저장 용량·사진 개수는 아직 약속하지 않는다.
- 해결한 항목은 삭제하지 않고 이력으로 남기며 두 플랜에서 조회할 수 있다. 보관은 별도 데이터 보존 정책을 따른다.
- 1개를 해결하면 무료에서도 새 항목을 작성할 수 있다. 기록 수를 채우려고 기록을 지우게 만들지 않는다.
- 인수인계 기록 작성과 판매 중지 적용은 구분한다. ‘에어컨 소음’ 메모만으로 임의 판매 중지하지 않는다. 사용자가 판매 중지 여부와 기간을 명시한다.
- 무료 기록 한도에 도달해도 긴급 판매 중지, 기본 상태 변경과 이미 열린 항목의 처리·해결은 가능하다.
- 객실 배정·판매 화면에서 미해결 중요 항목과 판매 중지 기간을 볼 수 있다. 판매 중지 객실은 경고만 띄우고 판매하는 것이 아니라 서버가 배정을 막는다.

### 3.4 객실·동·호텔

- 무료는 비보관 객실 20개까지 등록한다. 판매 중지·청소 중 객실도 20개에 포함한다. 일괄 생성과 보관 해제도 같은 한도를 검사한다.
- 프로는 객실과 동의 **상품상 수량 제한을 두지 않는다**. 한 번의 목록 조회·파일 업로드·요청 처리량에는 기술적 한도를 둘 수 있다.
- 호텔 → 동 → 층/객실의 구조를 사용한다. 동은 같은 호텔의 운영 구획이고 별도 호텔은 별도 property다.
- 같은 동 내 객실번호는 중복 금지다. A동 201호와 B동 201호는 허용하며 화면에는 동을 함께 표시한다.
- 예약·투숙·미래 판매 중지 등 살아 있는 참조가 있는 객실을 한도 회피 목적으로 보관할 수 없다. 과거 이력이 있는 객실은 물리 삭제 대신 보관한다.
- 여러 동을 가진 프로 호텔이 무료로 전환된다고 기존 동이나 객실을 자동 삭제·합병하지 않는다.

### 3.5 조직과 출퇴근

무료와 프로 모두 호텔 소유자·관리자·프런트·객실관리 등 역할별 구성원 초대, 소속 해제, 기본 권한 설정을 제공한다. 직원이 여러 호텔에 소속될 수 있지만 조회·작업 범위는 선택한 호텔로 한정한다.

프로는 출근·퇴근 기록, 근무 세션, 날짜별 기록, 수정 요청·관리자 승인, 기록 출력 기능을 제공한다. 본인은 자기 기록, 승인 권한자는 해당 호텔의 허용 범위만 조회한다.

- 기본안은 직원이 버튼으로 출퇴근을 기록하며 서버 시간을 쓴다.
- 자정 넘김·퇴근 누락·이중 출근·여러 기기의 동시 입력을 처리한다.
- 변경 전후 시간, 수정 이유, 요청자와 승인자를 보존한다.
- 직원의 호텔 소속을 해제해도 기존 근무 기록이 삭제되지 않는다. 접근 권한은 즉시 회수한다.
- 유료 종료 후 새 출근은 제한하되 이미 시작된 근무의 퇴근과 오류 정정은 허용한다. 과거 기록 조회·원본 출력도 유지한다.
- GPS 추적, 지문/얼굴 인증, 급여 계산, 노동법 적합성 판정은 초기 기능에 포함하지 않는다. 출퇴근 기록만으로 부정 출근 방지를 보장하지 않는다.

### 3.6 공통 기본 기능

두 플랜 모두 로그인, 호텔별 데이터 분리, 실시간 공유, 예약 중복 판매 방지, 변경 이력, 기본 권한, 개인별 접근 해제, 백업·복구 체계, 조회 범위 안의 원본 데이터 내보내기를 제공한다. 데이터 정확성과 기본 보안을 업그레이드 조건으로 삼지 않는다.

## 4. 기본 사용자 흐름

### 호텔 개설

계정 생성 → 호텔 이름·시간대 → 기본 동 → 객실 타입 → 객실번호 범위 생성 → 판매 채널·수수료 → 직원 초대 → 기존 예약 입력/가져오기.

무료로 21개 객실을 일괄 생성하려 하면 저장 전 20개 한도를 안내한다. 임의로 20개만 등록하지 않는다. 프로 구독 여부와 실제 객실 수를 호텔 설정에 함께 표시한다.

### 예약과 입실

현황판에서 날짜·타입·수량 선택 → 채널·금액·최소 고객 정보 입력 → 서버 검증 → 예약 확정 → 다른 기기에 갱신 → 체크인 전 객실번호 배정 → 입실.

판매 시에는 타입 수량을 예약하고 객실번호는 나중에 지정할 수 있다. 입실 시에는 실제 객실의 청소·시설·배정 충돌을 재검사한다. 연박 전체에 같은 객실을 배정할 수 없다면 객실 이동 필요를 명시하고 담당자가 확인한다.

### 객실 문제 처리

객실 상세 → 고장·컨디션 항목 작성 → 필요하면 판매 중지 기간 지정 → 담당자 처리 → 해결 기록 → 판매 재개를 별도 확인. 수리 완료가 자동으로 청소 완료나 판매 재개를 뜻하지 않는다.

### 유료 기능 진입

제한에 해당하는 작업에서 현재 사용량·한도·프로 기능을 설명한다. 이미 입력한 예약 초안은 유지하고 날짜 조정 또는 권한이 있는 담당자에게 문의할 수 있게 한다. 구독 결제는 소유자/구독관리 권한자만 한다. 직원에게 개인 결제를 요구하지 않는다.

## 5. 화면 구성

주요 메뉴는 현황, 예약, 객실, 리포트, 팀, 설정이다. 조직·출퇴근이 추가되어 v1의 5개 메뉴를 6개 업무 구역으로 확장한다. 모바일은 현황·예약·객실·더보기로 압축하고 더보기에 리포트·팀·설정을 둔다.

- 현황: 날짜별 전체·판매·잔여·중지, 타입별 재고, 입퇴실, 일일 금액, 미배정·고장·채널 수동 확인 경고.
- 예약: 달력/목록, 빠른 등록, 상세 수정·취소·부분 취소, 결제·환불, 객실 배정, 변경 이력.
- 객실: PC는 동·층별 그리드, 모바일은 동·층·타입 필터 목록. 객실 상세에 점유·청소·시설·인수인계 항목을 구분.
- 리포트: 무료는 일별, 프로는 기간 집계·추이·비교. 제안한 과거 범위 안에서 제공한다. 권한 없는 금액과 기간 밖 데이터는 서버 응답에서도 제외.
- 팀: 구성원과 역할, 프로 출퇴근·수정 승인. 사용하지 않는 모듈은 호텔 설정으로 숨길 수 있음.
- 설정: 호텔·동·객실·채널·수수료·권한·데이터 이전·구독/사용량. 동과 사업장을 혼동하지 않게 표시.

PC는 키보드 입력·대량 목록·검색에 맞추고, 모바일은 현장 터치·객실 확인·상태 변경에 맞춘다. 핵심 업무와 권한은 플랫폼 간 동일하게 유지한다. 가로로 긴 표를 모바일에 그대로 축소하지 않는다.

## 6. 기능 확장 원칙

기능은 각각 독립된 모듈과 권한 코드를 갖고, 구독 플랜은 그 기능을 사용할 수 있는지를 정한다. 호텔은 제공된 기능 중 실제 사용할 기능을 켜고 끌 수 있다. 가격 변경과 소프트웨어 배포가 꼭 묶이지 않도록 플랜 버전을 보존한다.

후속 후보는 청소 담당 배정, 점검 체크리스트, 사진·알림, 교대 인수인계 보드, 습득물, 소모품·린넨, 정산 대조, 다중 호텔 요약이다. **후보를 현재 프로에 이미 포함된 기능으로 광고하지 않는다.** 각각 문제·사용자·데이터·화면·권한·플랜·출시 조건을 정의한 뒤 추가한다.

초기 출시에서는 OTA 자동 연동, 도어록·키오스크, 인터넷 단절 중 예약 확정, 회계/급여 시스템, 고객용 예약몰을 제외한다. 데이터 구조와 연동 경계는 확장을 수용하되 미사용 기능을 먼저 구현하지 않는다.

## 7. 구독 전환과 데이터 보호

### 업그레이드

결제 제공자가 확인한 결제/구독 상태를 서버가 검증한 뒤 호텔의 권한 버전을 올린다. 모든 기기는 새 권한을 다시 받는다. 결제 완료 화면이나 클라이언트가 보낸 `pro=true`로 권한을 부여하지 않는다.

### 취소와 결제 실패

해지 신청은 원칙적으로 다음 갱신을 중지하는 예약이다. 이미 결제한 이용 기간까지 권한을 유지하는 안을 제안한다. 만료·결제 실패 시점과 유예 기간은 결제 수단 및 최종 판매 조건과 맞춰 확정한다. 구현이 임의로 무료 체험이나 유예 일수를 만들지 않는다.

### 무료 전환 시 기존 업무 보호

- 미래 기존 예약: 현재 플랜의 미래 한도 밖이어도 전환 전에 확정한 예약은 개별 조회, 결제 정리, 환불, 취소, 체크인·체크아웃, 객실 재배정이 가능하다. 같은 타입·박수·수량 범위의 운영상 재배정은 허용한다. 새 숙박일 추가·수량 증가·타입 변경으로 재고를 새로 소비하는 부분은 현재 한도를 검사한다.
- 과거 기존 예약: 조회 하한보다 오래된 일반 예약은 검색·달력·상세·일반 출력에서 제한하고 삭제하지 않는다. 현재 투숙 중이거나 미처리 환불·미수·정산 등 남은 업무가 있는 건은 권한 있는 담당자가 ‘미처리 업무’에서 필요한 정보와 관련 이력만 확인·완료할 수 있다. 완료 후 일반 조회는 현재 기간 제한을 따른다. 북마크한 예약이라는 이유로 예외를 주지 않는다.
- 객실: 20실을 초과해도 기존 예약과 입퇴실 업무를 유지한다. 소유자는 무료로 계속 판매할 객실 최대 20실과 동 1개를 선택한다. 선택 전에는 신규 판매를 잠시 보류하며 기존 예약 업무는 계속 가능하다. 선택 밖 객실은 기존 예약 소진과 관리·이력 조회만 허용한다.
- 미배정 예약: 전환 전 받은 타입별 예약을 처리할 수 있도록 기존 전체 객실에 대한 배정을 허용한다. 신규 무료 예약의 재고는 무료 판매 대상 객실의 날짜별 가용량을 기준으로 다시 계산하고 기존 예약 점유를 빠뜨리지 않는다. 자세한 계산은 기술 설계 5절을 따른다.
- 인수인계: 미해결 항목이 1개를 초과하면 모두 보존·조회·수정·해결할 수 있다. 미해결 0개가 되기 전까지 새 항목 추가와 재열기는 제한한다. 긴급 상태·판매 중지는 계속 허용한다.
- 출퇴근: 과거 기록 유지, 진행 중 근무 퇴근 허용. 신규 출근은 프로 재가입 후 가능하다.
- 보고서: 무료 전환 후 다일 집계는 제한하고 일별 조회는 무료의 과거 날짜 범위를 따른다. 기간 밖 개별 거래도 일반 조회에서 제한하며 원본은 보존 정책에 따라 유지한다. 과거에 출력한 파일을 사용자 기기에서 회수하지 않는다.

선택 결과를 객실 식별자에 저장하고 모든 입력 경로에서 같은 정책을 적용한다. 구독 전환으로 예약을 자동 취소하거나 임의의 객실을 무작위 숨기지 않는다.

### 보존과 탈퇴

무료 전환과 데이터 삭제는 별개다. 데이터 유형별 보관·파기·백업 잔존 기간과 고객의 내보내기·탈퇴 절차를 유료 출시 전에 확정한다. 무기한 보존을 약속하지 않으며 보관 정책과 개인정보 삭제 요구가 정해지면 감사 로그도 필요한 범위로 최소화·익명화한다.

## 8. 성공 기준

첫 호텔 파일럿 전, 동일한 작업의 현재 장부/엑셀 입력 시간과 실수·누락 사례를 기록한다. 파일럿에서는 같은 기준으로 비교한다.

- 예약 등록: 사전 설정과 로그인이 끝난 상태의 단순 1실 예약은 10초 이내를 초기 목표로 삼는다. 실제 현장에서 측정해 조정한다.
- 정확성: 마지막 1실 동시 판매, 예약 변경 실패, 취소·환불·월말 연박 검수에서 재고·금액 오류 0건.
- 공유: 안정적인 파일럿 네트워크에서 변경 확정 후 다른 활성 기기의 표시 갱신 p95 3초 이내를 초기 목표로 삼는다. 재연결 시 누락분을 조회한다.
- 인수인계: 판매 시 미해결 중요 항목을 발견할 수 있고, 고장으로 중지한 객실이 신규 판매되지 않는지 확인한다.
- 상품화: 프로 권한이 호텔·기기에 일관되고 무료 전환 후 기존 업무가 끊기지 않아야 한다.
- 유료 수요: 현장 검증 후 유사 숙박업소 3~5곳에서 실제 사용·가격 반응을 조사한다. 월 30,000원의 수익성을 검증 완료로 간주하지 않는다.

위 시간·속도는 목표이며 측정 결과가 아니다. 출시일과 개발 기간은 구현·파일럿 결과를 보고 정한다.

## 9. 개발 전에 남은 결정

현재 기준안으로 기반 개발을 시작할 수 있다. 아래 항목은 해당 기능 구현·판매 전에 확정한다.

1. 호텔당 과금, 무료 동 1개, 무료 전환 시 판매 객실 선택 정책의 채택 여부.
2. 매출 리포트의 과거 범위를 무료 1개월·프로 6개월로 맞추는 제안의 채택 여부. 출퇴근 기록 조회에는 예약 기간을 자동 적용하지 않는다.
3. 가격의 세금 표시, 결제 수단·취소·환불·유예·연간 결제·기존 고객 가격 정책.
4. 실제 호텔의 객실/동 구성, 사용 기기, 직원 역할, 연박·교대·정산 사례. 현재 데이터는 첨부에 없다.
5. 데이터 보관·탈퇴·기간 밖 자료 반환 정책, 모바일 앱 심사와 결제 방식.

이 항목들이 확인되기 전에는 ‘합의 완료’ 또는 ‘유료 출시 준비 완료’로 표시하지 않는다.

## 10. 근거와 v1 변경점

- 원본 1의 1~8절: 빠른 입력, 외부 OTA 미연동, 재고와 정산 분리, 현장 검증 원칙.
- 원본 2의 1~7절: 타입/실물 분리, 서버 재고 검증, 변경 이력, 권한, 화면 구조.
- 사용자의 추가 요청: 크로스플랫폼, 부분 유료화, 1/6개월, 1/30개, 20실/무제한, 출퇴근 기능.
- v1에서 뒤 단계로 두었던 호텔 격리·구독 권한의 데이터 구조를 첫 단계로 이동한다. 실제 결제 도입은 현장 검증 뒤에 한다.
- v1의 호텔 내 객실번호 유일성을 동 단위 유일성으로 수정한다.
- v1의 모든 기간 통계 기본 제공을 일별 무료/기간별 프로로 수정한다. 예약 과거·미래는 각각 무료 1개월·프로 6개월로 제한하며 리포트 범위도 일치시키는 안을 제안한다.
- v1의 웹 중심 배포에 Android/iOS 앱 패키징·실기기 검수를 추가한다.
- v1에 없던 무료 전환·기존 데이터·직원 근무 완료 처리 정책을 추가한다.

기술 근거와 공식 문서는 [개발·검수 계획](HOTORI-개발계획-v2.md)에 정리한다.
