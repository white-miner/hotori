# 호토리(HOTORI) 개발 인수인계서 및 그록봇 검토 요청

작성 기준: 2026-10-17 · 한국 시간 · 앱 버전 0.1.0

코드 기준 커밋: `e1cb0cc2bdd507d71ea55c45c0885564cacc3dc9`

커밋 메시지: `feat: build HOTORI local hotel operations draft`

이 문서는 기획과 실제 코드를 구분해 현재 상태를 전달하고, 다음 개발 방향에 대한 독립적인 의견을 받기 위한 자료다. 기능을 수정하거나 외부에 배포해 달라는 실행 지시가 아니다. 아래 마지막 절의 질문에 답해 주기 바란다.

## 1. 현재 상태를 먼저 요약

호토리는 호텔 현장의 엑셀·수기 장부를 대체하려는 객실 운영관리 서비스다. 현재는 **16실 가상 호텔을 대상으로 작동하는 PC·모바일 반응형 웹 초안**이 구현되어 있다.

예약과 객실 변경을 서버에 저장하고, 서버에서 재고·플랜 한도·버전 충돌을 검사한다. 운영 현황, 예약 관리, 객실 관리, 매출 리포트, 팀 관리, 호텔 설정의 6개 화면이 있다.

동일 코드 기준의 최종 자동 테스트 14개와 TypeScript·Vite 빌드가 통과했다. 별도 저장소 검수와 실제 브라우저 업무 흐름도 확인했다. 이것은 상용 PMS 전체 완성이나 실제 호텔 운영 안전성 보증을 뜻하지 않는다.

현재 실행 모델은 **한 PC·한 서버 프로세스·한 호텔·신뢰하는 로컬 데모 운영자**다. 실제 계정 인증, 직원별 접근 통제, 여러 호텔 격리, 인터넷을 통한 공동 사용, 결제·구독 검증, Android/iOS 설치형 앱은 구현 전이다.

가장 중요한 구조적 차이: 기획서는 정규화된 다중 호텔 PostgreSQL 구조를 목표로 하지만, 초안은 **PGlite의 단일 호텔 JSONB 집합 상태**로 구현했다. 이 차이를 다음 개발에서 어떻게 정리할지 검토받고 싶다.

## 2. 제품 배경과 브랜드

- 한글 이름: 호토리.
- 영문 이름: HOTORI. 개발 식별자: `hotori`.
- 브랜드 표현: `ホテル トータル レポート`.
- 제품 소개: 호텔 토탈 리포트 · 곁에 있는 운영 파트너.
- 방향: 복잡한 업무를 기억하고 운영자 곁에서 예약·객실·판매금·인수인계를 연결한다.
- 이전 기획서의 ROOMFLOW는 이전 가칭이다.

개발자는 호텔 현장의 예약 판매·취소·수수료·수기 장부 문제를 해결하고 싶어 한다. 첫 검증 장소는 실제 근무 호텔이다. 다만 호텔의 실제 객실 구성·업무 자료·고객 데이터는 아직 적용하지 않았고, 화면은 가상 데이터다.

최종적으로 PC, Android, iOS를 지원하고, 기능을 늘리면서 무료와 유료로 제공하려 한다. 초기 제품에는 외부 숙박 예약 사이트(OTA)의 자동 예약·취소·재고 API 연동을 넣지 않는다. 자체 서버 API와 직원 간 통신, 결제 서비스 통신까지 금지하는 요구는 아니다.

## 3. 사용자가 확정한 상품 요구

### 무료

- 예약 과거 조회 1개월, 미래 예약 관리 1개월. 두 방향 모두 제한한다.
- 객실 일일 판매금 조회.
- 객실별 미해결 인수인계 항목 1개.
- 객실 등록 20실.
- 호텔 조직 구성원 등록.

### 프로

- 월 30,000원 기준의 부분 유료화 플랜.
- 예약 과거 조회 6개월, 미래 예약 관리 6개월.
- 기간별 판매금 조회.
- 객실별 미해결 인수인계 항목 30개.
- 객실·건물동 등록의 상품상 수량 제한 없음.
- 조직 구성원 등록과 출퇴근 기록.

객실 기록 수는 객실마다 동시에 열려 있는 미해결 항목 수다. 해결 기록을 포함한 평생 누적 작성 수가 아니다.

### 개발 기준으로 제안했으나 별도 확정이 필요한 정책

- 호텔 한 곳당 하나의 구독을 적용하고 소속 직원·기기가 함께 사용한다.
- 무료는 기본 동 1개를 제공한다.
- 매출 리포트의 과거 조회 범위도 무료 1개월·프로 6개월로 맞춘다. 사용자가 직접 확정한 것은 예약의 과거·미래 제한이며, 매출 이력 범위는 개발 측의 추가 제안이다.
- 월 30,000원에 프로 기능을 묶어 제공한다. 가격의 세금 포함 여부, 판매 경로·환불·유예·기존 고객 가격 정책은 미확정이다.
- 무료 전환 시 기존 업무를 보호하고 신규 기능·판매만 현재 한도로 제한한다.
- 데이터 보관 기간과 앱에서 조회할 수 있는 기간은 분리한다. 구체적인 보관·파기·반환 정책은 미확정이다.

초안은 위 일부 제안을 체험 정책으로 적용했다. 체험 코드가 사업 정책 확정을 대신하는 것은 아니다.

## 4. 지금 실제로 사용할 수 있는 기능

### 운영 현황

날짜별 전체·판매·잔여·판매 중지 객실, 타입별 재고, 입퇴실 일정, 미배정 수량, 일일 판매금·수수료·예상 정산액, 미해결 인수인계 요약을 표시한다.

### 예약

고객명·연락처·타입·수량·기간·채널·객실당 1박 금액·메모로 등록한다. 확정 예약 전체 변경·전체 취소, 실제 객실 배정, 입실·예정일 퇴실이 가능하다. 퇴실하면 해당 객실은 청소 필요로 바뀐다.

판매 시 타입·수량으로 예약하고 객실번호는 나중에 지정할 수 있다. 재고는 숙박일별로 검사한다. 취소는 원본 삭제가 아니라 상태 변경이다. 청소가 끝나지 않았거나 시설이 정상이지 않은 객실의 입실을 막는다.

### 객실과 인수인계

객실번호·동·층·타입 등록, 청소 상태와 시설 상태 변경, 인수인계 접수·처리 시작·해결·재열기를 제공한다. 동 안에서 객실번호 중복을 막는다. 기록을 해결해도 이력은 남긴다.

시설 판매 중지는 현재 객실의 모든 향후 일정에 적용하는 단순 모델이다. 예약과 충돌하면 상태 변경을 거절한다. 기간별 판매 중지와 긴급 고장 예외 흐름은 아직 없다.

### 판매금 리포트

숙박일별 판매금·수수료·예상 정산액과 프로 기간 집계를 제공한다. 금액은 원 단위 정수다. 예약 당시 수수료율을 보관하고, 날짜별 수수료는 누적 반올림 차이로 배분해 일별 합계가 예약 수수료와 같게 한다.

객실당 동일 1박 요금 × 객실 수 × 박수 방식이다. 채널은 예시 고정 요율이며 설정 편집은 없다. 실제 수납·환불·OTA 입금 정산은 아니다. 예상 정산액을 순이익으로 취급하지 않는다.

### 팀·설정·체험 플랜

가상 구성원과 역할을 등록하고, 프로에서 서버 시각으로 출근·퇴근을 기록한다. 중복 출근을 막고, 무료로 전환해도 이미 시작한 근무는 퇴근할 수 있다.

호텔 이름 변경과 무료·프로 체험 전환이 가능하다. 이 전환은 실제 구독 결제·검증 기능이 아니다. 구성원의 역할은 데이터 항목이며 실제 접근 권한을 제한하는 기능은 아니다.

### 저장·오류 처리

데이터는 브라우저가 아니라 서버의 내장 PostgreSQL에 보관된다. 새로고침과 서버 종료·재시작 후에도 유지된다. 변경 버전과 요청 ID를 검사하고 오류·저장 상태를 화면에 표시한다.

## 5. 현재 기술 구성과 파일 안내

실제 설치 버전은 `package-lock.json` 기준이다. `package.json`의 버전 범위와 구분한다.

- Node.js 24.21.0 / npm 11.19.0: 개발 환경.
- React·React DOM 19.3.1 / TypeScript 5.9.3: 화면·타입.
- Vite 7.3.7: 웹 개발·빌드.
- Express 5.3.0 / tsx 4.23.15: TypeScript 로컬 서버 실행.
- PGlite 0.5.10: 내장 PostgreSQL 파일 저장.
- lucide-react 0.468.0: 아이콘.

주요 파일:

- `src/App.tsx`: 6개 화면, API 호출, 폼·모달, 요청 중복 방지·조회 상태. 현재 하나의 파일에 많은 역할이 모여 있다.
- `src/styles.css`: PC 사이드바·모바일 하단 메뉴와 반응형 스타일.
- `src/main.tsx`, `public/favicon.svg`: 웹 진입점과 아이콘.

- `server/domain.ts`: 날짜·플랜·예약·재고·배정·객실·인수인계·매출·근태 규칙과 가상 데이터.
- `server/store.ts`: PGlite 연결, 상태 읽기, 직렬 큐, 거래·요청 멱등 처리.
- `server/index.ts`: HTTP 경로, 로컬 Host/Origin·JSON 검사, 파일 잠금, 빌드 화면 서빙.
- `server/core.test.ts`: 14개 자동 테스트.
- `vite.config.ts`: 5173 웹 서버에서 3100 API로 프록시.
- `docs/HOTORI-제품기획-v2.md`, `HOTORI-기술설계-v2.md`, `HOTORI-개발계획-v2.md`: 목표 설계·정책·단계별 완료 조건. 모두 구현 완료 문서로 읽으면 안 된다.
- `docs/HOTORI-초안-실행안내.md`, `HOTORI-초안-검수.md`: 실제 초안의 실행·검수 근거.
- `docs/screenshots/hotori-desktop.jpg`, `hotori-mobile.jpg`: 검수한 PC·모바일 화면.

## 6. 저장 모델과 동시성 처리

실제 DB 테이블은 다음 두 가지다.

- `hotel_state`: `id=1`인 한 행의 `payload jsonb`에 호텔·객실·예약·인수인계·구성원·근무·감사 상태와 revision을 저장한다.
- `command_requests`: 요청 ID, 요청 내용 해시, 성공 결과, 생성 시각을 저장한다.

현재 예약은 `typeId`, `quantity`, `checkIn`, `checkOut`, `nightlyRate`, `roomIds`를 가진 집합 모델이다. 목표 설계의 `reservation_stays`, 날짜별 `reservation_nights`, 이동 구간·기간별 block 같은 관계형 엔티티는 아직 구현하지 않았다.

읽기와 쓰기는 한 프로세스의 Promise 큐를 공유한다. 변경 명령은 PostgreSQL 트랜잭션 안에서 요청 중복 검사 → 상태 행 `FOR UPDATE` → 업무 검증·변경 → 상태·감사 이력·요청 결과 저장을 수행한다. 실패 시 커밋하지 않는다.

이 구조에서 마지막 1실 동시 판매와 실패 원복을 검수했다. 그러나 단일 집합 상태를 모든 요청이 직렬 처리하는 모델이며 다중 서버·대규모 호텔 수에 대한 처리량과 분산 정합성을 검증한 것은 아니다.

서버 프로세스 중복 실행은 `.hotori-data/server.lock`으로 막는다. 데이터 폴더는 `.hotori-data/postgres`이며 Git과 검토 패키지에 넣지 않는다. 자동 백업·복구·스키마 마이그레이션·감사 보존 정책은 아직 없다.

## 7. API와 중요한 구현 규칙

### HTTP 계약

- `GET /api/health`: 로컬 데모·저장 방식·인증 전제 상태.
- `GET /api/state?date=YYYY-MM-DD`: 호텔, 플랜, 한도, 객실·예약·기록·팀·근무·감사·현황.
- `GET /api/reports?start=YYYY-MM-DD&end=YYYY-MM-DD`: 종료일 포함. 무료는 시작일=종료일.
- `POST /api/commands`: JSON `{type, data, requestId}`. 변경 성공은 `{message, id?, revision}`, 오류는 HTTP 오류와 `{error, code}`.

명령군은 예약 생성·변경·취소·배정·입퇴실, 객실 생성·상태 변경, 항목 생성·변경, 호텔 이름, 가상 구성원, 출퇴근, `demo.plan`이다. 정확한 문자열과 필드는 `shared/types.ts`·`server/domain.ts`를 확인한다.

### 날짜·플랜

호텔 날짜는 Asia/Seoul 기준이고, 숙박일 점유는 `[체크인, 체크아웃)`이다. 월은 30일/180일이 아니라 달력 월로 더하고 빼며 월말은 말일로 보정한다.

예를 들어 2026-10-17 기준 무료 조회 하한은 9월 17일, 신규 숙박 마지막 날짜는 11월 16일, 체크아웃은 11월 17일까지다. 프로는 과거 4월 17일부터, 신규 숙박은 2027년 4월 16일과 4월 17일 체크아웃까지다.

과거 한도 밖 일반 예약은 응답과 연결 감사 기록에서 제외한다. 경계 연박은 허용 구간의 금액만 보이고 전체 일정 수정을 잠근다. 오래된 미퇴실 업무는 금액·연락처를 가린 운영 참조로 남겨 퇴실할 수 있게 한다.

프로에서 받은 미래 예약은 무료 전환 뒤에도 기존 업무를 처리할 수 있게 보존한다. 무료에서 생성한 예약을 프로에서 먼 미래로 변경한 경우도 서버의 보호 태그를 유지한다. 이는 일반 신규 예약 한도를 해제하는 기능이 아니다.

무료 전환 시 20실 초과 호텔은 신규 판매를 보류한다. 무료로 사용할 최대 20실을 선택하는 화면·재고 정책은 아직 구현 전이다. 미해결 항목과 근무 원본은 지우지 않고 처리·종료를 허용한다.

### 객실과 금액

예약과 객실 배정을 이중 차감하지 않는다. 실물 배정 겹침과 청소·시설 상태를 검사한다. 연박은 같은 객실에 연속 배정 가능한지 보수적으로 검사하며, 객실 이동이나 기존 배정 최적화는 지원하지 않는다.

객실 1실·1박 금액은 0원도 유효하다. 날짜별 다른 가격, 부분 취소, 추가요금·할인·위약금·환불은 후속 범위다.

### 요청 재시도와 화면 갱신

서버는 요청 ID와 내용 해시를 영속 저장한다. 클라이언트는 응답이 불확실한 동일 명령을 재시도할 때 같은 ID를 재사용한다. 이 클라이언트 대기 정보는 메모리 ref이므로 브라우저 전체 재시작을 넘는 복구까지 보장하지 않는다.

조회는 최초 진입과 명령 후·날짜 변경 시 수행한다. 현재 다른 탭·다른 직원에게 자동으로 push하는 실시간 공유 기능은 없다.

## 8. 보안·서비스 전제

서버와 웹은 127.0.0.1에만 바인딩한다. Host/Origin 허용 목록과 JSON 변경 요청 검사를 두고 wildcard CORS를 열지 않았다. 비밀키나 실제 결제 자격 증명은 사용하지 않는다.

이 조치는 로컬 경계이며 계정 인증·호텔별 데이터 격리·직원별 권한을 대신하지 않는다. 현재 요청은 모두 같은 로컬 데모 운영자의 작업이다. `demo.plan`도 이 전제에서만 존재한다.

상용 배포 전에 서버 측 실제 사용자·호텔 소속·작업 권한·구독 권한을 결합해야 한다. 현재 서버를 인터넷에 공개하는 것만으로 공동 사용 서비스를 만들 수 없다.

## 9. 실행·검수·Git 상태

작업 폴더에서 의존성을 재현하려면 `npm ci`를 사용한다. Node.js·npm이 설치되어 있어야 한다.

```powershell
npm ci
npm run dev
```

웹은 `http://127.0.0.1:5173/`, API는 `http://127.0.0.1:3100`이다. 개발 서버를 종료하고 빌드 결과를 한 서버에서 확인하려면 다음과 같이 실행한다.

```powershell
npm run build
npm start
```

이 경우 접속 주소는 `http://127.0.0.1:3100/`이다. 개발 서버와 빌드 서버를 동시에 시작하지 않는다. `npm run preview`는 별도 제공하지 않는다.

```powershell
npm test
```

Git은 로컬 `main` 브랜치이며 기준 코드 커밋은 문서 상단과 같다. 원격 저장소·GitHub 연결은 없다. 이 인수인계서와 검토 패키지는 그 기준 코드 이후에 만든 전달 자료다.

## 11. 다음 개발 방향에 대한 현재 가설

아래는 검토를 요청하는 우선순위 초안이며 확정된 개발 일정은 아니다.

1. 현장 사례 확인: 실제 객실·동·채널·교대·연박·정산 사례와 초안의 업무 차이를 정리한다.
2. 코드 정리: 화면·API 상태·명령 처리를 분리하고, 테스트로 현재 동작을 고정한다. 예약·재고·금액·권한 경계를 유지한다.
3. 저장 모델 전환 설계: 호텔·객실·예약의 실물 단위·숙박일·요금·배정·판매 중지·사용자 소속을 정규화한다. 기존 샘플/파일 데이터의 이행 경로도 정한다.
4. 공동 사용 기반: 실제 인증, 호텔 소속·권한과 서버 격리, 클라우드 DB, 배포·백업·복구, 변경 전파를 갖춘다.
5. 실무 핵심 예외: 부분 취소·객실 이동·긴급 고장·금액 조정 중 현장 빈도가 높은 것을 우선 완성한다.
6. 허가받은 호텔 파일럿 뒤 결제·무료 전환·모바일 앱 출시를 단계적으로 진행한다.

이 순서보다 먼저 해결해야 할 위험이나, 초안 검증 단계에서는 뒤로 미뤄도 되는 작업이 있는지 의견을 받고 싶다.

## 12. 그록봇에게 요청하는 검토

당신은 숙박업 운영 소프트웨어와 웹 서비스 아키텍처를 검토하는 독립 리뷰어다. 위 문서와 첨부 소스를 근거로 다음 질문에 답해 주기 바란다. 칭찬이나 일반적인 기능 제안보다 현재 구현에 영향을 주는 판단을 원한다.

1. **집중할 문제:** 예약 재고·인수인계·매출·근태 중 첫 호텔에서 가장 먼저 검증할 가치는 무엇인가? 어떤 현장 자료가 있어야 판단할 수 있는가?
2. **현재 구조의 수명:** 단일 호텔 JSONB 집합 상태와 직렬 큐를 어느 검증 단계까지 유지해도 되는가? 다중 호텔·직원 공동 사용 전 반드시 분리해야 할 요소와 단계적 이행 방법은 무엇인가?
3. **예약 모델:** 타입 수량과 실제 객실 배정을 분리하면서 부분 취소·객실 이동·일별 요금·수용 부족을 지원하려면 어떤 최소 데이터 모델이 필요한가? 현재 기록을 어떻게 이행할 것인가?
4. **데이터 정확성:** 연박의 보수적 배정 검사, 미퇴실·판매 중지 처리, 과거 조회 경계, 수수료 배분·재시도·버전 비교에서 빠진 위험과 추가 검수 사례는 무엇인가?
5. **무료·프로 정책:** 예약 과거·미래 1/6개월, 객실 20실/무제한, 미해결 항목 1/30개, 기간 리포트·근태 유료화가 현장 사용을 어떻게 바꾸는가? 무료 전환 때의 업무 보호와 상품 가치가 충돌하는 지점은 무엇인가?
6. **공동 사용과 보안:** 실제 인증·호텔별 격리·직원 권한·실시간 공유를 넣는 순서와 최소 출시 기준을 제안해 달라. 로컬 데모의 안전 장치를 상용 보안으로 오인하지 말아 달라.
7. **플랫폼:** 현재 React·TypeScript 웹을 유지하면서 Android/iOS 설치형으로 확장하는 방향을 평가해 달라. 지금 결정할 것과 현장 검증 후 결정할 것을 나눠 달라.
8. **유료 출시:** 월 30,000원 상품을 검증하려면 사용성·운영 비용·지원 부담 측면에서 어떤 지표와 실험이 필요한가? 시장 가격·스토어 정책 같은 외부 사실은 최신 근거와 추론을 구분해 달라.
9. **다음 개발 묶음:** 지금 코드에서 다음에 실행할 작업을 3단계로 나누고, 각 단계의 완료 조건과 반드시 필요한 테스트를 적어 달라. 근거 없는 확정 일정·전면 재작성 권고는 피하고 그 필요성을 설명해 달라.

### 원하는 답변 형식

- 현재 상태에 대한 짧은 판단.
- 유지할 선택과 수정할 선택을 근거와 함께 구분.
- 우선 해결할 문제 최대 5개: 위험도, 발생 조건, 영향, 수정 방향, 확인 방법.
- 다음 3단계 실행안과 단계별 완료 조건.
- 판단에 필요한 추가 질문 최대 5개.

소스에서 확인한 사실, 문서에서 전달받은 사실, 추가 자료가 필요한 추정을 구분해 달라. 직접 실행하지 않았다면 테스트 통과를 확인했다고 쓰지 말아 달라. 기획서에 있는 기능을 이미 구현된 기능으로 간주하지 말아 달라.

## 13. 전달 자료 안내

이 문서만 전달하면 현재 상태·설계 방향에 대한 검토를 받을 수 있다. 구체적인 코드 리뷰를 받으려면 함께 만든 `HOTORI-그록봇-개발검토패키지-2026-10-17.zip`도 첨부한다. 압축파일을 읽을 수 없는 환경이면 다음 파일부터 별도 첨부한다.

1. `server/domain.ts`, `server/store.ts`, `shared/types.ts` — 업무·저장 계약.
2. `server/index.ts`, `server/core.test.ts` — HTTP 경계와 자동 검수.
3. `src/App.tsx` — 화면·API·폼 상태.
4. `package.json`, `package-lock.json`, 기획서·검수 기록·화면 이미지 — 실행 재현과 배경.

패키지는 소스·설정·기획·검수·이미지와 이 문서의 스냅샷이다. `node_modules`, `dist`, `.git`, `.hotori-data`, 환경 파일·로그는 포함하지 않는다. 로컬 DB나 실제 호텔 운영 자료를 전달하는 패키지가 아니다.

`127.0.0.1`은 개발 PC의 주소다. 그록봇이 이 주소나 프로젝트 상대 경로만으로 파일에 접근할 수 있다고 가정하지 말고 실제 첨부한 자료를 기준으로 검토한다.
