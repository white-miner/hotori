# 스마트등록 출처·타입 차이 및 삭제 입구 (2026-10-30)

## 원인과 변경
스마트등록의 신규 타입 인식과 기존 예약의 저장값은 별개였다. 기존 예약번호가 일치하면 중복 생성 방지를 위해 업로드를 건너뛰므로, 이전 인식 오류로 저장된 타입은 새 인식값으로 자동 변경되지 않는다. 예약 수정창은 저장값을 그대로 읽고 있었다.

- `shared/smartRegister.ts`: 기존 예약과 미리보기 타입 차이를 식별한다. 기존 예약은 자동 덮어쓰지 않고 수정 입구를 제공한다. 신규 가져오기 메모에는 `[스마트등록]`을 붙이며, 기존 가져오기 메모 형식도 읽는다. 원문 타입이 없으면 추정하지 않는다.
- `src/BookingImportInfo.tsx`: 스마트등록 라벨과 객실 타입 원문을 공통 표시한다.
- `src/Entry.tsx`: 접힌 예약 관리 옆으로 예약 삭제 버튼을 이동하고 기존 최종 확인 단계를 보존한다. 출처·원문·저장 타입 차이를 표시하며, 인식 타입 적용은 편집값만 바꾸고 저장 시 반영한다.
- `src/SmartRegister.tsx`, `src/Dashboard.tsx`: 기존예약 행에서 저장 타입과 새 인식 타입이 다르면 경고와 기존 예약 수정 버튼을 표시한다. 기존 중복 방지 유지.
- `src/NowRoomCard.tsx`, `src/NowSidePanel.tsx`: 카드에는 출처 라벨(클릭하면 상세 원문), 객실 상세·선택 패널·미배정 목록에는 출처와 원문을 표시한다. 외부 공유에는 출처 원문을 노출하지 않는다.
- `src/styles.css`: 라벨, 원문 표시, 삭제 입구, 타입 차이 안내 배치. 카드 4:5 유지.
- `shared/smartRegister.test.ts`, `src/detailedRoomCard.test.tsx`: 신규 타입 보존, 기존 불일치와 중복 방지, 출처 판별, 공유 비노출 회귀 검증.

## 실제 UI 검증
- 사용자 승인 후 해당 미배정 예약 **1건만** 일반 스탠다드에서 스탠다드 2PC로 저장하고 다시 열어 확인했다. 날짜 10/29→10/30, 판매금 90,000원, 미배정 상태 및 가져오기 원문 유지. 결제 등록·예약 삭제는 실행하지 않았다.
- 수정창: 삭제 버튼이 접힌 영역 밖에 노출된다. 클릭 시 영구 삭제 확인 단계가 열리고 삭제 취소로 닫히는 것을 확인했다.
- 기존예약 미리보기: 저장값과 다른 타입의 원문을 검증용으로 붙여넣어 차이 안내와 기존 예약 수정 연결을 확인했다. 업로드하지 않았으며 검증용 붙여넣기는 비웠다.
- 1920×1080: 실제 스마트등록 객실카드의 라벨과 이름이 겹치지 않으며 카드 168×210(4:5) 유지. 라벨 클릭 시 상세창에 실제 원문 표시.
- 좁은 화면: 수정창의 삭제 버튼 및 출처·원문 줄바꿈 확인.
- 화면 증거는 개인정보를 포함해 Git에 올리지 않음: `test-results/frontdesk-2026-10-30/import-source-corrected.png`, `import-source-fhd.png`.

## 검증과 제한
- 전체 자동 테스트 820개 통과, 실패 0개. TypeScript·Vite·서버 빌드 통과.
- DB 컬럼·마이그레이션 없음. 기존 메모 저장 경로를 활용한다.
- 예전 스마트등록 예약은 가져오기 메모가 남아 있는 경우에 출처와 원문을 표시할 수 있다. 원문이 유실된 예약의 타입이나 출처를 임의 복원하지 않는다.
- 다른 기존 예약의 타입은 자동 변경하지 않는다. 원문과 저장값을 비교해 직원이 확인한 뒤 정정한다.
