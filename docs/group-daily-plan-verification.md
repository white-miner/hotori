# 단체 날짜별 객실·요금 등록 검증 (2026-10-30)

## 조사 결과
기존 `Booking`은 예약별 `checkIn`, `nights`, `nightRates`를 가지며 `groupId`로 묶인다. 단체 정산도 객실별 박 요금을 합산하므로 서로 다른 퇴실일과 계약 단가를 이미 지원한다. 그러나 `GroupEntry`는 모든 객실에 공통 기간을 주어 저장하므로 6실→4실 구성을 만들려면 등록 후 개별 수정이 필요했다.

## 구현
기존 단체 등록창의 ‘간단 예약 / 호실까지’ 옆에 ‘날짜별 객실·요금’을 추가했다. 첫 숙박일과 일정 종료일을 정하고 실제 설정에 있는 타입을 선택한 뒤, 날짜별 실 수와 객실당 요금을 적는다. 날짜별 소계·입실/예정 퇴실 수·남는 재고·전체 청구 합계를 확인하고 기존 단체 저장 경로로 저장한다.

실 수가 줄면 뒤 순번 예약부터 예정 퇴실하고, 남은 예약은 연박으로 이어진다. 증가하면 새 입실 예약을 만든다. 0실인 날을 지나 다시 늘면 별도 예약이 생긴다. 각 예약의 기간과 박 요금은 독립적이며 저장 후 기존 화면에서 호실 배정 및 객실별 수정이 가능하다. 대표객실이 다른 예약 데이터를 소유하지 않는다. 예정 퇴실일만으로 실제 퇴실 처리하지 않는다.

## 파일
- `shared/groupDailyPlan.ts`: 날짜별 실 수·요금을 독립 예약으로 구성, 입력값·실 수 한도 검증.
- `shared/groupDailyPlan.test.ts`: 사용자 사례 및 증가·감소·빈 날짜·입력 오류·정산/재고 회귀 검증.
- `src/GroupDailyPlanFields.tsx`: 타입 선택, 날짜별 실 수·단가, 소계·재고·입퇴실 요약.
- `src/GroupEntry.tsx`: 새 입력 방식, 기존 단체 저장·정산 경로 재사용, 중복 제출 방지.
- `src/styles.css`: 날짜별 입력 표와 합계 영역 스타일.
- `package.json`: 새 테스트를 전체 테스트 명령에 포함.

## 사용자 사례의 실제 결과
목요일 스탠다드 3실×60,000원 + 욕조 3실×70,000원 = 390,000원. 금요일 스탠다드 2실×80,000원 + 욕조 2실×90,000원 = 340,000원. 총 6개 예약, 10객실박, 청구 730,000원.

- 스탠다드: 2박 140,000원 두 예약 + 1박 60,000원 한 예약.
- 욕조: 2박 160,000원 두 예약 + 1박 70,000원 한 예약.
- 금요일 예정 퇴실 2실, 토요일 예정 퇴실 4실. 짧은 예약에 금요일 요금이 들어가지 않음.
- 타입별 3실인 격리 설정에서 목/금/토 잔여는 각각 0/1/3실.
- 단체 원장의 청구 730,000원, 실제 결제 0원. 수납 내역을 만들거나 배분하지 않음.

## 실제 UI 및 자동 검증
- 실제 앱의 ‘간단 예약 → 상세 → 단체 → 날짜별 객실·요금’ 입구 확인.
- 실제 `GroupEntry`와 `ConfirmHost`를 사용한 격리 메모리 저장 화면에서 4개 날짜·타입 행을 입력하고 저장한 6개 예약의 날짜·박별 요금·재고·단체 청구를 확인했다. 운영 DB에 예시 예약을 생성하지 않았다.
- 기존 ‘간단 예약’ 방식의 타입 수 입력 및 `GroupRoomRates` 진입 유지 확인.
- 전체 테스트 823개 통과, 실패 0개. TypeScript·Vite·서버 빌드 통과.
- 증거: `test-results/frontdesk-2026-10-30/group-daily-input.png`, `group-daily-saved.png` (격리 UI). 운영 UI 증거와 함께 최종 응답에 제공.

## 범위와 제한
DB 컬럼·마이그레이션 없음. 기존 단체 저장 API와 예약별 요금 모델을 그대로 쓴다. 이 화면은 새 단체 예약의 빠른 등록 경로다. 이미 저장된 단체의 일정을 일괄 덮어쓰거나 실제 체크인·체크아웃·수납을 자동 실행하지 않는다. 호실은 등록 후 기존 배정 기능에서 지정한다. 기존 저장 API의 DB 전체 트랜잭션 보장 범위를 확대하지 않았다.
