## 1. 사용자가 객실카드에 요구한 것 (최종 사양 목록)

출처 표기: [문서] = repo 문서에 적힘, [대화] = 사용자가 대화에서 지시한 내용을 개발 담당이 문서/커밋에 옮겨 적은 것. 사용자 발언 원문 보관은 이 repo에 없습니다.

1. 카드는 "그 객실, 그 날짜의 상태 한 장"입니다. 기준 사진은 다른 PMS(StaySync)의 객실 화면입니다. [문서: `room-card-spec.md` §1, `room-card-concept.md`]
2. 표시 순서: 객실번호 → 이용기간(+박수) → 결제 방식·금액 → 손님 이름 → 회사 → 박당 요금. [문서: spec §2]
3. 모든 객실카드에는 그 객실 **자기 하루(박당) 요금**이 보입니다. 총액·평균·추정은 안 보입니다. 예: 602 ₩70,000, 501/301 ₩80,000. 박마다 다르면 "변동". [대화 → 문서: spec §5, `room-card-price-report.md` §6]
4. 색: 객실 가격=빨강, 받은 돈=검정, 받아야 할 돈(미수금)=파랑. [대화 → 커밋 `e194db8`, spec §3]
5. 받아야 할 돈은 **오늘 밤까지**의 미수금입니다. 아직 묵지 않은 밤은 미수금이 아닙니다. [대화 → `cb9d2a0`, `91397d8`]
6. 대표객실 카드: 이용기간(`10/25~10/27`)과 박수, 단체 결제(`이체690,000`), "대표객실" 표시. 표시에 마우스를 올리거나 누르면 연동 객실 번호 목록. [대화 → price-report §6, spec §4]
7. 단체의 다른 객실 카드: 객실번호, 이용기간, 자기 박당 요금, 대표객실을 가리키는 `건물+호수`(예: `본관 602호`). "대표객실"이라는 글자는 대표객실에만. [대화 → `77343a3`, spec §4]
8. 개인·회사(기관) 카드도 자기 박당 요금을 보입니다. 회사명은 선택 입력이고 카드에 표시. [대화 → `0538107`, `2d76c02`]
9. 플랫폼(OTA) 예약: 카드에 플랫폼 이름 + 판매금액(예: `야놀자270,000`). 플랫폼 예약번호는 카드에 표시하지 않음. 단체로 플랫폼 결제한 경우 "각 객실 카드에 자기 금액" (사용자가 4개 질문 중 4번에 이렇게 답함). [대화 → `9634006`, `6fbf9aa`]
10. 퇴실 미정(열린 숙박)은 `10/25 ~`로 표시, 몇째 밤은 `4박째`. 퇴실예정으로 취급하지 않음. [대화 → `77343a3`, spec §5]
11. 건물 이름은 일반 카드에 붙이지 않음(건물별로 보는 화면이 따로 있음). 건물+호수는 다른 객실을 가리킬 때만. [대화 → `f373165`]
12. 카드를 선택하면 상세와 수정이 열림. 모든 값은 입력 후에도 확인·수정 가능해야 함(기록 정정). [대화, `room-card-concept.md` 8]
13. 총액을 객실 수·박수로 균등 분할하지 않음. 요금은 객실별·박별로 다름. 청구(객실 요금)와 결제는 분리해 차액만 비교. [대화 → `98ac546`, `4585eba` 등]
14. 글자는 읽혀야 합니다. 이 항목은 처음엔 명시되지 않았고, 사용자가 실제 화면(스크린샷)을 보내고 나서야 확정 요구가 됐습니다("가격이 엄청 작아지고, 뭐가 뭔지 알 수 없다"). [대화 → `53dfc76`, spec §2-1]

## 3. 실패별 원인, 못 잡은 이유, 수정

공통 "못 잡은 이유"(F1~F10에 모두 해당): 아래 세 가지는 개별 항목에서 반복하지 않습니다.
- **P1. 테스트가 통과했고 화면은 안 봤습니다.** `shared/*.test.ts`는 함수 반환값을 비교합니다. "화면에서 크기·줄·색이 사양대로 읽히는가"를 확인하는 테스트는 `68e1a4f` 이전엔 없었습니다. `68e1a4f`에서 `src/roomCard.test.tsx`가 생겼지만 이것도 문자열/클래스 비교입니다.
- **P2. 사양이 한 장의 문서가 아니었습니다.** 카드 사양 문서 `room-card-spec.md`는 `68e1a4f`(12:25)에 처음 생겼고, 그 전엔 대화로 전달된 요구가 커밋마다 조각으로 반영됐습니다.
- **P3. 조각 패치.** 각 커밋이 "지금 지적된 한 가지"만 고쳤고, 같은 카드에 영향을 주는 다른 사양(색, 단체, 플랫폼, 퇴실 미정)을 한 번에 대조하지 않았습니다. 가장 큰 증거는 현황 카드와 배치 카드가 서로 다른 값을 계산한 것입니다(F10).

### F1. 하루 요금 대신 합계가 보임
- 증상: 카드 금액이 박당 요금이 아니라 총액/잔금/최근 결제액/숙박 합계.
- 원인(코드): `shared/nowboard.ts` `nowAmountGlance`가 처음부터 "금액 한 줄"만 반환했고(개별 잔금/최근 결제액/총액), `98ac546`은 단체 객실을 `stayNightAmounts(b)` 합계로 바꿨을 뿐입니다. 박별 요금표(`booking.nightRates`)는 저장돼 있었지만 카드는 읽지 않았습니다. 상세: `docs/room-card-price-report.md` §1~§3.
- 못 잡은 이유: P1~P3. 추가로 `98ac546`은 문제를 "누구의 돈이냐(단체 vs 객실)"로 해석했고 "단위가 무엇이냐(박 vs 전체)"를 확인하지 않았습니다(price-report §3).
- 수정: `655703f`(`nowNightRate`, `RoomCardFacts`), 현재는 `shared/roomCard.ts`의 `roomCardModel` → `nowNightRate`.

### F2. 플랫폼 결제금액이 카드에서 사라짐

## 5. 외부 검토자에게 묻는 설계 질문

### 5-1. 방 보호(`hold_ahead`) 의미

(c) 기본값 1일이 사용자에게 "형식 강요"인가? 설계 문서에는 "사용자 확인 필요(결정 1)"로 남아 있고 닫히지 않았습니다.

### 5-2. 단체 구성원 카드의 플랫폼 금액 표시

### 5-3. 단체 객실 요금표의 "제안" 값이 가격으로 집계되는 문제

### 5-4. 총액 균등분할이 남아 있는 곳 (표시·계산용)
`splitAmountLast`(나머지는 마지막 박)가 아래에서 쓰입니다. 입력 UI는 아니지만, 박별 요금표가 없는 예약에서 청구·표시에 균등값을 만듭니다.
- `shared/periodPay.ts` `stayNightAmounts`(55행): 박별 요금표가 없으면 `splitAmountLast(b.price, total)`. 호출처 `shared/groupLedger.ts`, `shared/nowboard.ts` (청구 박별 계산용이라 "표시만"이 아닙니다.)
- `shared/issuanceNightDetail.ts`: 발급 서류(견적·청구서)의 객실×날짜 단가에서 총액만 있으면 `splitAmountLast`, 표시용 `unitRateFromCells`는 평균(`Math.round(합/칸 수)`), 총액 기준 재분배 함수.
- `shared/scheduledMove.ts` `retargetLegRate`, `legCharges`: `Math.round(b.price / n)`을 박별 표의 기본값으로 사용.
- 질문: 박별 요금이 없는 구 예약의 청구를 어떻게 다뤄야 하는가(균등, 입력 요구, 미정 표시)? 사용자 규칙은 "총액을 균등 분배하지 않는다"인데, 발급 서류와 청구 계산에는 아직 균등이 남아 있음.

### 5-5. 기타
- 카드 정보량 vs 가독성: 한 사실 한 줄, 박당 요금 17px 빨강이 사양인데, 한 카드에 번호, 기간, 연동/결제, 받을 돈, 이름, 회사, 박당 요금, 단체 결제 버튼이 모두 들어가면 줄 수가 많아 카드 높이가 늘 수 있음(렌더 그림으로만 확인, 실제 데이터 미확인). StaySync 사진은 카드가 더 작습니다.
- "받을 돈"이 0이면 줄이 사라짐(결제 완료를 별도로 표시하지 않음). 사용자 확인 필요.
- 사양에 StaySync의 "몇째 밤" 표시를 넣은 것은 사용자 확정이 아니라 `room-card-concept.md` 9번의 "검토" 항목에서 개발 담당이 진행한 것입니다(`68e1a4f`). 사용자의 명시 승인은 이 repo에서 확인되지 않습니다.
