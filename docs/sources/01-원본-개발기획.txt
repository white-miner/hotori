# 호텔 객실 운영관리 시스템 개발 기획

API 없는 독립형 PMS · 모바일/PC 통합 · 바이브 코딩 기반

이 아이디어는 지금까지 논의했던 사업들과 성격이 다르다.

당신은 호텔 현장에서 객실 판매와 취소, 플랫폼별 수수료, 수기 장부의 문제를 직접 경험하고 있다. 따라서 고객이 어떤 불편을 겪는지 추측할 필요가 상대적으로 적다.

또한 이 프로그램은 처음부터 대형 호텔의 모든 업무를 처리하는 PMS(Property Management System)가 될 필요가 없다.

우선 소규모 숙박업소가 엑셀이나 장부 없이 객실 재고와 판매금액을 정확하게 관리할 수 있는 도구를 만드는 것이 핵심이다.

다만 한 가지 기술적 한계를 먼저 명확히 해야 한다.

API를 사용하지 않으면 야놀자·여기어때·아고다·부킹닷컴 등 외부 숙박 플랫폼의 판매·취소 정보를 자동으로 수신하거나, 해당 플랫폼의 판매 가능 객실 수를 자동으로 변경할 수 없다.

따라서 프로그램 내부에서는 팀원 간 실시간 동기화가 가능하지만, 외부 플랫폼과의 재고 일치 여부는 사용자가 입력한 정보에 의존한다.

이 제약을 인정한 상태에서도 기존 엑셀과 수기 장부보다 훨씬 편리한 프로그램은 충분히 만들 수 있다.

## 5. 가장 중요한 것은 예약과 재고를 계산하는 알고리즘이다

이 프로그램이 엑셀을 대체하려면 화면보다 데이터의 정확성이 우선이다.

예를 들어 10월 17일 체크인, 10월 19일 체크아웃 예약은 17일과 18일의 객실 재고를 차감하고 19일의 재고는 차감하지 않는다.

2박 예약의 재고 반영 방식

10.17

판매

10.18

판매

10.19

재판매

10.20

재판매

핵심 계산 규칙은 다음과 같다.

\\[ \text{판매 가능 객실} = \text{전체 객실} - \text{유효 예약 객실} - \text{판매 중지 객실} \\]

단, 모든 값은 해당 숙박일과 객실 타입을 기준으로 계산해야 한다.

또한 취소된 예약은 객실 재고에서 복구하되, 취소 이력과 취소 수수료는 삭제하지 않는다.

예약 변경 역시 기존 기록을 덮어쓰는 대신 변경 전후 내역을 남긴다.

### 반드시 대비해야 하는 예외 상황

- 예약 취소와 재예약이 동시에 발생하는 경우
- 두 명의 직원이 마지막 객실을 동시에 판매하려는 경우
- 예약된 객실 타입을 다른 타입으로 변경하는 경우
- 연박 예약 중 일부 날짜만 변경하거나 취소하는 경우
- 객실 점검으로 판매 중지했다가 다시 판매하는 경우
- 플랫폼별 수수료가 예약 시점이나 상품에 따라 달라지는 경우
- 고객이 현장에서 추가 요금을 지불하거나 환불받는 경우

특히 팀원이 동시에 예약을 등록할 때는 서버에서 재고를 다시 확인하고 하나의 거래로 확정해야 한다. 화면에서 잔여 객실이 1개라고 보인다고 해서 두 명 모두 예약을 성공 처리해서는 안 된다.

## 6. 매출과 정산금액은 반드시 분리해야 한다

기존 엑셀에서 자주 혼동할 수 있는 부분이다.

예를 들어 고객이 객실을 10만 원에 예약하고 플랫폼 수수료가 12%라면 다음과 같다.

| 항목      | 금액       |
| ------- | -------- |
| 객실 판매금액 | 100,000원 |
| 플랫폼 수수료 | 12,000원  |
| 예상 정산액  | 88,000원  |

이때 88,000원을 호텔의 순이익이라고 표시해서는 안 된다. 인건비, 세금, 객실 운영비 등이 차감되지 않았기 때문이다.

따라서 대시보드에는 최소한 총 판매금액, 플랫폼 수수료, 예상 정산액, 실제 입금액을 별도로 표시해야 한다.

또한 일별 매출은 숙박일 기준과 예약 접수일 기준을 구분할 수 있어야 한다. 월별 통계에서는 월말을 넘기는 연박 예약도 정확하게 배분해야 한다.

외부 숙박 플랫폼 API는 사용하지 않더라도, 모바일과 PC 사이에서 데이터를 주고받으려면 자체 서버 통신은 필요하다. 만약 어떠한 API 통신도 금지한다면 여러 기기의 실시간 공유는 사실상 불가능하다.

개발 도구로는 기존 소리앱 작업에 익숙한 Flutter를 재사용할 수도 있지만, 이 제품은 데이터 입력과 테이블 관리가 중심이므로 React 기반 PWA도 충분히 검토할 만하다.

## 8. 실제 개발은 3단계로 나누는 것이 좋다

MVP · 핵심 객실관리

객실 타입 설정, 예약 등록·변경·취소, 잔여 객실 계산, 채널별 수수료, 일별 매출, 과거 검색, 다중 사용자 동기화.

가장 먼저 실제 호텔에서 검증할 버전

2차 · 운영 편의성 확장

월별·연별 통계, 파일 일괄 가져오기, 예약 중복 탐지, 정산 관리, 객실 점검 상태, 직원별 작업 이력.

3차 · 상품화

호텔별 독립 계정, 셀프 가입, 자동 결제, 데이터 내보내기, 사용 가이드, 다중 사업장 관리, 고객 지원 체계.

바이브 코딩으로 화면과 기본 CRUD 기능은 빠르게 구현할 수 있다. 하지만 재고 중복 판매 방지, 금액 계산, 동시성 제어, 접근 권한과 백업은 자동 생성된 코드만 믿지 말고 별도의 테스트를 해야 한다.

특히 실제 호텔 데이터를 적용하기 전에는 가상 예약을 수백 건 생성해 날짜별 재고와 정산이 정확한지 검증하는 것이 좋다.

## 9. 사업으로서의 가능성

이 프로그램은 당신의 다른 아이디어보다 문제와 사용 장면이 구체적이라는 강점이 있다.

다만 기술적으로 만들 수 있다는 것과 숙박업소가 유료로 구매한다는 것은 별개다.

예를 들어 다음 가격은 시장 검증을 위한 가정이다.

| 유료 사업장 | 월 39,000원 | 월 59,000원 |
| ------ | --------- | --------- |
| 20곳    | 78만원      | 118만원     |
| 50곳    | 195만원     | 295만원     |
| 100곳   | 390만원     | 590만원     |
| 200곳   | 780만원     | 1,180만원   |

이는 비용과 세금을 차감하기 전 매출이다.

또한 API 없이 운영하는 프로그램은 외부 플랫폼의 예약 변경을 자동 반영하지 못한다. 따라서 기존 채널매니저를 완전히 대체하는 상품으로 판매하기보다 엑셀·수기 장부를 대체하는 경량 객실 운영 시스템으로 포지셔닝하는 편이 현실적이다.

첫 목표는 100개 호텔 확보가 아니다.

당신이 근무하는 호텔에서 실제로 사용했을 때 엑셀보다 예약 등록이 빠르고, 잔여 객실 계산 오류가 줄어드는지 확인하는 것이다. 실제 운영 데이터 적용에는 호텔의 허가와 적절한 개인정보 보호가 필요하다.

그다음 유사한 규모의 숙박업소 3\~5곳에서 사용성을 검증하면 된다.

## 10. 개발 전에 반드시 결정할 한 가지

지금 요구사항에서 가장 중요한 설계 분기점은 객실을 어떤 단위로 관리하느냐다.

객실 관리의 기본 단위를 어떻게 설정할까?

A. 타입별 수량 관리

스탠다드 10개 중 7개 판매, 3개 잔여처럼 객실번호 없이 수량 중심으로 관리

B. 객실번호별 관리

201호, 202호처럼 실제 객실을 지정하고 판매·점검·체크인 상태를 관리

C. 두 방식 모두 지원

타입별 판매 가능 수량을 기본으로 표시하고 필요할 때 객실번호를 배정

이 방식으로 상세 개발 설계&#x20;

내 추천은 C 방식이다.

대부분의 숙박업소에서는 판매할 때 객실 타입과 수량이 중요하지만, 실제 체크인과 객실 점검에서는 객실번호가 중요해진다. 두 개념을 분리해 설계하면 10실 규모의 소형 숙박업소부터 100실 규모의 호텔까지 같은 프로그램을 사용할 수 있다.

이 구조를 처음부터 정확하게 설계하는 것이 이후 기능을 계속 추가하는 것보다 훨씬 중요하다.
