# 호텔 객실관리 시스템 구현 명세서

ROOMFLOW · Product Requirements & Technical Specification v1.0

개발 목표: 10\~100개 이상의 객실을 운영하는 숙박업소가 엑셀이나 수기 장부 없이 객실 예약, 판매 가능 수량, 판매 채널, 수수료, 정산, 과거 이력을 하나의 시스템에서 관리할 수 있는 모바일·PC 통합 프로그램을 구축한다.

핵심은 타입별 객실 수량 관리와 객실번호별 실물 관리의 분리다.

예약을 받을 때는 스탠다드 1실, 디럭스 2실처럼 타입과 수량으로 판매하고, 고객이 입실할 때는 201호, 202호처럼 실제 객실을 배정한다.

이를 통해 객실번호를 아직 정하지 않았더라도 판매 가능한 수량을 정확하게 계산할 수 있고, 현장에서는 실제 객실 상태까지 관리할 수 있다.

## 개발 기본 원칙

확정 설계

외부 OTA API 연동 없음. 사용자가 입력하거나 승인한 데이터만 예약 재고에 반영한다.

예약 재고는 날짜·객실 타입 단위로 계산. 실제 객실번호 배정은 별도 관리한다.

모든 수정은 기록으로 남김. 예약 취소, 금액 변경, 객실 변경은 삭제하지 않는다.

모바일과 PC에서 같은 데이터 사용. 여러 직원이 동시에 조작해도 중복 판매를 방지한다.

호텔별 데이터 분리 · 트랜잭션 · 실시간 알림 · 백업

권장 기술은 React + TypeScript 기반 PWA, PostgreSQL, 서버 측 예약 트랜잭션, 실시간 WebSocket 또는 변경 이벤트 구독이다.

Supabase 같은 백엔드 서비스를 사용할 수도 있지만 특정 업체에 종속되지 않도록 예약 계산 규칙은 별도 서비스 계층에 구현한다.

외부 OTA API를 사용하지 않는다는 조건과 자체 서버 통신은 양립한다.

## 2. 데이터베이스 설계

예약의 정확성을 확보하려면 객실 타입, 실물 객실, 예약, 객실 점유, 판매 채널, 금액을 분리해야 한다.

### 핵심 데이터 테이블

| 테이블                   | 주요 필드                                                           | 역할           |
| --------------------- | --------------------------------------------------------------- | ------------ |
| `properties`          | id, name, timezone, currency                                    | 숙박업소         |
| `room_types`          | id, property_id, name, active                                   | 객실 타입        |
| `rooms`               | id, room_type_id, room_number, active                           | 실제 객실        |
| `room_blocks`         | room_id, start_date, end_date, reason                           | 판매 중지 기간     |
| `channels`            | id, property_id, name, active                                   | 예약 플랫폼·현장    |
| `channel_fee_rules`   | channel_id, rate, fixed_fee, effective_from                     | 채널별 수수료 규칙   |
| `reservations`        | id, property_id, code, status, guest_name, channel_id           | 예약 헤더        |
| `reservation_items`   | id, reservation_id, room_type_id, quantity, check_in, check_out | 예약별 객실 수량    |
| `reservation_nights`  | item_id, stay_date, room_type_id, amount                        | 날짜별 객실 점유·매출 |
| `room_assignments`    | item_id, room_id, start_date, end_date                          | 실제 객실 배정     |
| `reservation_charges` | reservation_id, amount, category                                | 추가 요금·할인     |
| `payments`            | reservation_id, amount, method, status                          | 고객 결제·환불     |
| `settlements`         | reservation_id, expected_amount, paid_amount, status            | 플랫폼 정산       |
| `users`               | id, email, name                                                 | 사용자          |
| `property_members`    | property_id, user_id, role                                      | 호텔별 권한       |
| `audit_logs`          | actor_id, entity, entity_id, before, after, timestamp           | 변경 이력        |

모든 호텔별 데이터에는 `property_id`를 직접 또는 상위 관계를 통해 연결한다. 서버에서 호텔 접근 권한을 검증해야 하며, 단순히 화면에서 다른 호텔의 데이터를 숨기는 것만으로는 충분하지 않다.

### 필수 데이터 제약

- 같은 호텔 내 객실번호 중복 금지.
- 체크아웃 날짜는 체크인보다 늦어야 한다.
- 예약 수량은 1 이상.
- 금액은 원 단위 정수로 저장하고 부동소수점 계산을 피한다.
- 예약 상태는 서버가 허용한 전이만 가능.
- 객실 배정 기간이 겹치는 예약은 원칙적으로 금지.
- 취소·환불·금액 변경은 감사 로그에 남긴다.
- 모든 변경 작업은 고유 요청 ID를 사용해 중복 저장을 방지한다.

`reservation_nights`는 예약 생성·변경 시 날짜별로 만들어지는 점유·금액 기록으로 사용한다. 판매 중지와 객실 배정까지 포함한 최종 가용 재고는 서버에서 계산한다.

## 3. 객실 재고 계산 엔진

### 3-1. 타입별 수량 관리

가상 호텔에 다음과 같은 객실이 있다고 가정하자.

2026년 10월 17일 숙박 기준

예시

스탠다드

2실 가능

전체 12 · 예약 9 · 중지 1

디럭스

4실 가능

전체 10 · 예약 6 · 중지 0

스위트

4실 가능

전체 8 · 예약 3 · 중지 1

계산의 기본식은 다음과 같다.

\\[ A(t,d)=C(t,d)-R(t,d)-B(t,d) \\]

- \\(A\\): 타입 t의 날짜 d 판매 가능 객실 수
- \\(C\\): 해당 날짜에 유효한 전체 객실 수
- \\(R\\): 해당 날짜 예약으로 점유된 수량
- \\(B\\): 예약과 겹치지 않는 판매 중지 객실 수

단, 예약된 객실을 동시에 판매 중지 처리하면 단순 차감으로 중복 계산될 수 있다. 따라서 판매 중지와 예약이 충돌할 경우 자동으로 재고를 이중 차감하지 않고 관리자에게 해결을 요구해야 한다.

### 3-2. 객실번호별 관리

실제 객실은 다음과 같은 상태를 가진다.

| 구분 | 상태                   |
| -- | -------------------- |
| 예약 | 미배정 / 배정 완료          |
| 점유 | 공실 / 투숙 중            |
| 청소 | 청소 필요 / 청소 중 / 준비 완료 |
| 시설 | 정상 / 점검 / 판매 중지      |

예약 상태와 청소 상태는 서로 다른 개념이다.

예를 들어 201호는 오늘 체크아웃 예정이면서 동시에 청소가 필요한 상태일 수 있다.

따라서 `room.status` 하나에 모든 상태를 넣지 않는다. 예약·점유·청소·시설 상태를 별도로 관리한다.

### 3-3. 객실번호 배정 규칙

객실번호는 예약 시점에 필수로 입력하지 않는다.

고객 체크인 전 또는 체크인 시점에 배정할 수 있다.

객실 배정 시에는 다음을 검증한다.

1. 예약된 타입과 실제 객실 타입이 일치하는가?
2. 해당 숙박 기간에 다른 예약이 배정되어 있지 않은가?
3. 판매 중지 기간과 겹치지 않는가?
4. 객실이 실제 입실 가능한 청소·시설 상태인가?

타입 변경이나 업그레이드는 별도 승인 동작으로 처리한다.

중요: 타입별 잔여 수량이 있다고 해서 항상 특정 객실을 연박 전체 기간에 배정할 수 있는 것은 아니다. 날짜별로 객실이 다르게 비어 있을 수 있기 때문이다. 따라서 연박 예약 시에는 연속 배정 가능 여부를 확인하고, 객실 이동이 필요하면 명시적으로 표시해야 한다.

### 화면 A. 현황판 — 프로그램의 첫 화면

최상단에 날짜 선택기를 배치하고, 다음 정보를 즉시 표시한다.

- 전체 객실 / 예약 객실 / 잔여 객실 / 판매 중지 객실
- 타입별 판매 가능 수량
- 오늘 체크인·체크아웃·투숙 중 객실
- 오늘 예약 접수금액과 해당 숙박일 매출
- 채널별 판매 수량
- 미배정 객실, 중복 입력 의심, 정산 미확인 경고

PC에서는 타입별 현황과 예약 목록을 나란히 배치한다. 모바일에서는 타입별 현황을 먼저 보여주고 예약 목록을 아래에 배치한다.

### 화면 B. 예약 등록 및 변경

예약 등록 플로우

날짜 선택 → 객실 타입·수량 선택

예약 채널 → 금액 → 예약자 정보

서버 재고 검증 → 예약 확정

현황판·통계·예약 목록 자동 갱신

예약 상세 화면에는 `수정`, `취소`, `객실 배정`, `결제 기록`, `변경 이력` 버튼을 제공한다.

예약 취소 시 확인 모달을 표시하며, 취소 수수료와 환불 여부를 선택할 수 있도록 한다.

UX 규칙: 기존 예약을 수정하기 위해 삭제 후 재등록하는 작업을 요구하지 않는다.

### 화면 C. 객실 관리

PC에서는 객실번호를 층별 그리드로 표시한다.

모바일에서는 타입별로 접을 수 있는 목록을 제공한다.

객실을 누르면 객실번호, 타입, 오늘 예약, 투숙 상태, 청소 상태, 시설 점검 여부, 최근 변경 기록을 표시한다.

### 화면 D. 매출·정산 통계

통계 화면 구성 예시

당월 객실 매출

## 4,850만원

가상 데이터

예상 정산액

## 4,320만원

가상 데이터

조회 기간은 일·주·월·년·사용자 지정으로 선택한다.

필수 지표는 객실 판매 수량(객실박 기준), 판매율, 객실 평균 판매단가(ADR), 판매 가능 객실당 매출(RevPAR), 총 판매금액, 예상 수수료, 예상 정산액, 실제 입금액이다.

매출은 기본적으로 숙박일에 배분한 금액으로 계산하되, 예약 접수일 기준 판매 실적과 실제 입금일 기준 현금흐름을 별도로 제공한다.

### 화면 E. 설정

최초 설치 시 설정 마법사를 제공한다.

1. 호텔명과 영업일 마감 기준시간 설정
2. 객실 타입 등록
3. 객실번호 등록 또는 일괄 생성
4. 예약 플랫폼과 수수료 규칙 등록
5. 팀원 초대 및 권한 지정
6. 기존 예약 데이터 입력 또는 파일 가져오기

예를 들어 101\~110호를 입력할 때 10개 객실을 각각 등록하지 않고 범위 입력으로 생성할 수 있어야 한다.

100실 규모에서도 개별 객실 등록을 강제하지 않는다.

## 5. 플랫폼별 수수료 및 정산 엔진

예약 플랫폼은 고정된 목록으로 만들지 않는다.

사용자가 원하는 이름으로 무제한 등록할 수 있어야 한다.

예시:

| 플랫폼   | 수수료율      | 추가 수수료 |
| ----- | --------- | ------ |
| 야놀자   | 사용자 설정    | 선택     |
| 여기어때  | 사용자 설정    | 선택     |
| 아고다   | 사용자 설정    | 선택     |
| 부킹닷컴  | 사용자 설정    | 선택     |
| 현장 카드 | 카드 수수료 설정 | 선택     |
| 현장 현금 | 0%        | 선택     |
| 전화 예약 | 사용자 설정    | 선택     |

플랫폼마다 수수료 산정 기준이 다를 수 있으므로 단순 퍼센트뿐 아니라 다음을 지원한다.

- 정률 수수료와 건당 고정 수수료
- 수수료 부과 대상 금액 설정
- 플랫폼 할인과 숙박업소 부담 할인 구분
- 세금 포함 여부 및 반올림 규칙
- 예약별 수수료 직접 수정
- 계약 변경 시 적용 시작일 설정
- 예상 정산액과 실제 입금액 대조

과거 예약의 수수료는 현재 설정을 바꿨다고 재계산하지 않는다. 예약 당시 적용된 수수료 규칙을 별도로 보존해야 한다.

또한 카드 결제와 현금 결제는 판매 채널과 구분한다. 예를 들어 전화 예약이면서 카드 결제인 경우도 존재하기 때문이다.

## 6. 예외 상황 및 처리 정책

| 상황           | 프로그램의 처리                            |
| ------------ | ----------------------------------- |
| 마지막 객실 동시 예약 | 서버에서 하나만 확정, 나머지는 재고 부족 표시          |
| 예약 취소        | 재고 복원, 원본과 취소 기록 보존                 |

| 타입 변경        | 신규 타입 재고 확인 후 원자적으로 변경              |

| 플랫폼 중복 예약    | 이름·날짜·금액 등 유사성 경고, 자동 삭제 금지         |
| 인터넷 연결 끊김    | 조회 가능한 캐시만 제공, 신규 확정 예약은 서버 연결 후 처리 |
| 직원 실수        | 권한에 따른 수정 및 변경 이력 조회                |
| 월말 연박        | 숙박일별 객실 매출 배분                       |
| 노쇼           | 재고 점유와 위약금·환불을 별도 처리                |
| 예약 없이 현장 입실  | 현장 판매 예약 생성 후 객실 배정                 |
| 객실 이동        | 날짜별 배정 이력 유지, 중복 점유 검사              |
| 환불           | 원거래를 삭제하지 않고 환불 거래 별도 기록            |

### 동시 예약 처리 원칙

서버에서 동일 호텔·객실 타입·숙박일 범위에 대해 직렬화 가능한 트랜잭션 또는 명시적 잠금을 사용한다.

재고 확인과 예약 확정은 반드시 하나의 트랜잭션으로 실행한다.

클라이언트 화면에서 잔여 객실이 보인다는 이유만으로 예약을 확정해서는 안 된다.

예약 재시도 요청에는 멱등성 키를 사용해 네트워크 오류로 동일 예약이 두 번 생성되는 것을 방지한다.

### 재고 충돌 정책

기본 정책은 초과 예약 금지다.

호텔이 의도적으로 오버부킹을 허용하려면 관리자 전용 설정과 명시적 승인, 변경 이력을 요구한다. MVP에서는 오버부킹 기능을 제공하지 않는 편이 안전하다.

## 7. 사용자 권한 및 보안

| 기능       | 관리자 | 매니저 | 직원 |
| -------- | --- | --- | -- |
| 예약 등록·조회 | ✓   | ✓   | ✓  |
| 예약 변경·취소 | ✓   | ✓   | 제한 |
| 객실 배정    | ✓   | ✓   | ✓  |
| 청소·점검 상태 | ✓   | ✓   | ✓  |
| 매출 통계    | ✓   | ✓   | 제한 |
| 수수료 설정   | ✓   | 제한  | —  |
| 직원 관리    | ✓   | —   | —  |
| 감사 로그    | ✓   | 조회  | —  |
| 데이터 내보내기 | ✓   | 제한  | —  |

실제 권한은 역할명만으로 처리하지 않고 서버의 작업별 권한으로 검증한다.

예약자 이름·연락처 등 개인정보는 필요한 범위에서만 저장하고, 직원별 조회 권한과 보존 기간을 설정한다. HTTPS, 암호화된 백업, 접근 기록, 세션 만료, 계정 차단 기능도 필요하다.

다중 호텔 SaaS로 발전시키는 경우에는 데이터베이스 수준의 호텔별 접근 제한과 자동화된 격리 테스트를 추가한다.

## 8. 개발 우선순위 및 일정

기능을 모두 동시에 구현하면 복잡도가 급격하게 높아진다. 따라서 실제 호텔에서 사용 가능한 최소 제품을 먼저 완성하고, 검증된 기능만 확장한다.

| 단계            | 개발 범위                         | 완료 조건                 |
| ------------- | ----------------------------- | --------------------- |
| P0 · 데이터 기반   | 호텔, 객실 타입, 객실번호, 계정, 권한, DB   | 호텔별 설정 저장·불러오기 성공     |
| P1 · 예약 엔진    | 예약 등록·변경·취소, 날짜별 재고, 중복 판매 방지 | 동시 예약·연박·부분 취소 테스트 통과 |
| P2 · 현황판      | 타입별 잔여 수량, 객실번호 현황, 모바일 UI    | 예약 후 모든 화면에 즉시 반영     |
| P3 · 정산       | 채널별 수수료, 판매금액, 정산액, 환불        | 계산 결과와 기준 데이터 일치      |
| P4 · 이력·통계    | 검색, 감사 로그, 일·월·연 통계           | 과거 거래 복원 및 집계 검증      |
| P5 · 운영 안정화   | 백업, 복구, 파일 가져오기, 보안           | 실제 운영 시나리오 검수 통과      |
| P6 · SaaS 상품화 | 셀프 가입, 구독 결제, 호텔별 데이터 분리      | 독립된 여러 호텔 운영 가능       |

초기 개발에서는 P0\~P4를 핵심 MVP로 설정한다. P5의 기본 보안·백업은 운영 투입 전 필수이며, P6는 실제 사용성과 유료 수요가 확인된 이후 진행한다.

바이브 코딩을 사용하더라도 구현 기간을 확정할 근거는 아직 없다. 개발 환경과 기존 코드 재사용 여부에 따라 달라지므로 각 단계의 완료 조건을 통과한 뒤 다음 단계로 진행한다.

## 9. 자동 테스트 및 검수 기준

코드가 존재한다는 사실은 개발 완료의 기준이 아니다.

사용자가 화면에서 기능에 진입하고, 작업을 수행하고, 정확한 결과를 확인할 수 있어야 완료다.

## 10. 개발자 및 AI 코딩 에이전트 전달 지침

아래 내용은 Codex, Claude Code, Cursor 등 개발 에이전트에 전달할 핵심 구현 원칙이다.

# ROOMFLOW 개발 실행 지침

## 프로젝트 목적

엑셀 및 수기 장부를 대체하는 호텔 객실 판매·재고·정산 관리 PWA를 개발한다.

대상은 10\~100실 이상 규모의 숙박업소이며, 객실 타입별 수량 관리와 객실번호별 실물 관리를 동시에 지원한다.

## 절대 준수 조건

1. 외부 숙박 플랫폼 API를 사용하지 않는다.
2. 자체 서버 통신과 팀원 간 실시간 동기화는 허용한다.
3. 객실 타입·객실 수·객실번호·플랫폼·수수료는 사용자 설정으로 관리한다.
4. 예약 데이터는 날짜별 객실 재고와 일관성을 유지해야 한다.
5. 중복 판매 방지는 반드시 서버 트랜잭션으로 구현한다.
6. 예약 취소·수정·환불은 원본 기록을 삭제하지 않고 이력을 보존한다.
7. PC와 모바일 모두에서 동일한 기능을 사용할 수 있어야 한다.
8. 초보 사용자도 직관적으로 조작할 수 있도록 입력 단계를 최소화한다.
9. 모든 기능은 실제 UI에서 입력부터 결과 확인까지 검증한다.
10. 새로운 기능을 추가하기 전에 기존 기능의 데이터 정합성을 검증한다.

## 구현 순서

**1차: 기반**

- React + TypeScript PWA 구성
- PostgreSQL 스키마 및 마이그레이션
- 로그인·호텔별 권한
- 객실 타입·객실번호·판매 채널 설정

**2차: 핵심 기능**

- 예약 등록·수정·취소
- 날짜별 타입 재고 계산
- 객실번호 배정
- 동시 예약 충돌 방지
- 모바일·PC 실시간 동기화

**3차: 정산·이력**

- 플랫폼별 수수료 규칙
- 숙박일별 매출 계산
- 결제·환불·정산 기록
- 과거 예약 검색
- 변경 감사 로그
- 일·월·연 통계

**4차: 안정화**

- 자동 테스트
- 접근 권한 검증
- 백업·복구
- CSV 가져오기·내보내기
- 모바일 터치 사용성 개선

## 개발 방식

각 단계는 다음 순서로 진행한다.

1. 구현 범위와 데이터 계약 정의
2. 데이터베이스 및 서버 로직 구현
3. 단위·통합 테스트
4. 사용자 UI 연결
5. 브라우저 실제 조작 검수
6. 모바일 화면 검수
7. 완료 보고 및 다음 단계 승인

코드가 존재하더라도 UI에서 사용할 수 없으면 미완료로 처리한다.

데이터베이스 오류, 예약 재고 불일치, 계산 오류를 임시 UI 처리로 숨기지 않는다.

운영 데이터 적용 전에 예약 동시성, 중복 입력, 날짜 변경, 부분 취소, 수수료 변경, 데이터 복구 테스트를 통과해야 한다.

## 최종 목표

직원은 예약을 빠르게 입력하고, 관리자는 모든 객실의 판매 가능 수량과 판매금액을 확인하며, 여러 직원이 동시에 사용해도 데이터가 정확하게 유지되는 호텔 운영 시스템을 완성한다.

## 11. 제품 설계에서 추가로 권하는 두 가지

첫째, 기존 엑셀 데이터 이전 기능을 중요하게 다뤄야 한다.

엑셀을 오래 사용한 숙박업소는 기존 예약을 새 프로그램에 다시 입력해야 한다면 도입을 꺼릴 수 있다. 따라서 CSV·엑셀 파일을 가져와 열을 매핑하고, 중복 예약을 검토한 뒤 승인하는 기능이 필요하다.

다만 엑셀마다 형식이 다르므로 처음부터 모든 양식을 자동 인식하겠다고 약속하지 않는다.

둘째, 외부 플랫폼 재고 불일치 경고가 필요하다.

API가 없으면 외부 플랫폼에 남아 있는 객실 수를 확인할 수 없다. 하지만 프로그램에서 예약을 등록한 직후, 직원에게 어떤 플랫폼의 재고를 수동으로 조정해야 하는지 안내할 수 있다.

예를 들어 다음과 같은 형태다.

외부 플랫폼 재고 확인 필요

10월 17일 스탠다드 객실이 1개 판매되었습니다.

해당 타입의 남은 객실은 2개입니다. 연결되지 않은 판매 채널의 노출 재고를 확인하세요.

플랫폼 재고 확인 기능 상세 설계&#x20;

이것은 외부 플랫폼 재고를 자동으로 수정하는 기능이 아니다. 수동 확인의 누락을 줄이는 작업 관리 기능이다.

### 최종 개발 방향

ROOMFLOW의 경쟁력은 기능이 많은 데서 나오지 않는다.

복잡한 숙박업소 운영을 직원이 이해하기 쉬운 몇 가지 동작으로 바꾸는 데서 나온다.

그 핵심은 타입별 예약 수량과 실제 객실번호를 분리하면서도, 두 데이터가 서로 충돌하지 않도록 만드는 것이다.

첫 버전의 성공 기준은 단순하다.

프런트 직원이 예약을 등록하면 타입별 잔여 객실이 정확히 변경되고, 다른 직원이 즉시 확인할 수 있으며, 관리자는 언제든 해당 예약의 판매금액과 변경 이력을 찾을 수 있어야 한다.

이 기준이 완성된 다음에야 SaaS 판매, 자동 결제, 다중 호텔 관리 기능으로 확장하는 것이 합리적이다.
