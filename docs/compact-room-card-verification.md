## 데이터 구조·영향

새 테이블·필드·마이그레이션 없음. 관리기록은 기존 `room_memos.kind=delivery`와 save/setStatus/구독을 재사용한다. 인수인계에 남긴 내용도 같은 기록 목록에서 볼 수 있고 해결한 과거 기록을 숨기지 않는다. 호텔 공용(null roomId) 또는 실제 객실에 연결하며 기존 120자 제한을 따른다.

예약 조회/등록/수정/삭제·결제·입퇴실 데이터 명령은 변경하지 않았다. 대표는 기존 단체 관리 포인터이며 객실 예약은 각각 유지한다. 기존 기기별 G 표시번호/순서 저장 방식도 변경하지 않았다.

## 실제 UI 검증

사용자가 로그인한 로컬 HOTORI와 실제 데이터로 검증했다. 임의 41실/예시 객실을 만들지 않았다. 실제 본관 40+별관 19=59실, 8층 배치다.

- 1920×1080, DPR 1: 카드 약 171.5×214.375px. 전체 59실의 폭/높이 비율 0.8(4:5, 서브픽셀 반올림 오차 이내). 8개 층 각각 한 줄, 가로 넘침 없음. 카드 내부 가로/세로 넘침 0.
- 번호 26px/흰색, 이름·금액 18px, 상세 요약 16px, 버튼 글씨 16px/높이 42px. 층 이름 22px와 1px 실선, 설정 색상 막대 확인.
- 반복 라벨/단체 없는 빈 영역/공실번호 나열/상단 전체·임시만 제거 확인. 카드 위를 덮던 상단 패널은 현황에서 static으로 변경.
- 상세보기 → 701 객실 상세: 실제 타입·단체/대표·날짜와 시간·박수·총액/박당 요금·결제 확인. 예약 상세·수정 → 기존 수정하기 화면 → 저장 없이 닫기 확인.
- 빠른 업무 → 해당 객실의 기존 좌측 업무 패널 열림 확인.
- 퇴실예정 → 기존 퇴실 확인 팝업 → 취소 확인. 실제 퇴실 처리하지 않음.
- 설정 → 본관 6층 → 파랑을 노랑으로 변경 → 저장됨 → 9개 번호 및 층 막대 갱신 → 새로고침 후 유지 → 원래 파랑으로 복원 → 모든 층 색상 스냅샷 일치.
- 실제 4실 단체 선택 → 4실 강조. 단체 객실만 → 9실. 해제/전체 → 59실 복귀.
- 관리기록 실제 새 글 저장 → 목록 즉시 1건 → 해결 처리 → 새로고침 → 해결된 기록 그대로 표시. 검증 사실을 적은 개발 검증 기록 1건을 해결 상태로 보관했다. 이 전후 59개 예약 카드 표시 텍스트 스냅샷 전체가 동일했다.
- 확인사항 탭 → 기존 자동 경고 122건과 고치기/이대로 둠/복원 입구 유지, 중첩 모달 없이 한 모달 내부 표시. 실제 자동 고치기·무시·대량 퇴실은 실행하지 않음.
- 등록·수정·삭제·체크인/체크아웃은 운영 예약을 시험용으로 변경하지 않았다. 기존 데이터 명령의 회귀 테스트를 사용했다.

## 산출물·한계

실제 예약 정보가 포함된 캡처는 공개 저장소에 커밋하지 않고 로컬 `deliverables/`에 보관한다: `hotori-compact-cards-fhd.jpg`, `hotori-compact-details-fhd.jpg`, `hotori-compact-checkout-fhd.jpg`, `hotori-management-records-fhd.jpg`, `hotori-management-retry-isolated.jpg`, `hotori-compact-evidence.json`.

- FHD 레일 사이드바에서는 전체 한 층이 한 줄에 들어간다. 사이드바 고정 또는 좁은 데스크톱에서는 최소 168px를 지키기 위해 층별 가로 스크롤을 허용한다.
- 긴 이름/타입/단체명은 요약 말줄임이며 전체 상세창에서 원문을 확인한다. 시간·결제 내역·메모 등은 합의대로 상세창으로 이동했다.
- 기기별 G 표시번호/순서의 다중 기기 동기화는 별도 서버 설계가 필요하다.
- 80cm 물리적 시청 거리는 사용자의 실제 모니터 검토가 필요하다.
- 단체 연결/해제 데이터 명령은 이번 변경에서 수정하지 않았다. 운영 예약 연결을 시험 해제하지 않았고 기존 초기 검증 기록의 격리 해제 검증과 기존 회귀를 유지했다.
