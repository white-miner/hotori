# 검색 객실 이동·일괄 퇴실 및 요금 입력 조사

검증일: 2026-10-31 KST. 기준 main 73740f4. 실제 운영 데이터는 조회·진입·취소만 검증했으며 이동·퇴실·결제 쓰기를 실행하지 않았다.

## 구현

- 객실 빠른 업무의 `객실 이동 · 검색해서 선택`, 운영 패널의 기존 객실 이동, 이동 중 하단의 `객실 검색`에서 동일한 선택창을 연다.
- 호실·타입 검색, 건물·층·타입 필터, 같은 타입·층·건물 우선 정렬. 조회 중 선택·입력값 유지.
- 숙박 전체 / 선택일부터 이동을 명시하며 출발·목적지·적용 기간·다른 타입 여부를 확인한다. 1박은 전체 이동만 가능하다.
- 빈 객실 이동과 숙박 전체 맞교환을 별도 탭으로 구분한다. 기존 boardMove/boardMoveWindow/proposeRoomSwap 및 확인·되돌리기 흐름을 재사용한다.
- 선택한 기간의 점유·객실 임시마감과 퇴실 미정의 미래 객실 보호 기간을 검사한다. 저장 직전에 최신 예약·배치·상태와 목적지를 재검사한다.
- 이동 저장은 기존 setPlacement의 room_id/room_segments만 사용한다. 예약 번호·기간·약정 요금·총액·결제·단체 연결을 수정하지 않는다. 부분 이동 이전 구간을 보존한다.
- 맞교환은 기존 순차 저장을 사용한다. 실패/응답 유실 때 A를 비우고 B→A 순으로 원배치를 복구한다. 복구 자체가 실패하면 숨기지 않고 두 예약 확인을 안내한다. 새 DB 트랜잭션·마이그레이션은 없다.
- 현황 제목 옆 `퇴실예정 일괄 퇴실`: 실제 오늘 영업일·전체 건물의 기존 nowLists/canCheckOut 기준 대상만 표시한다. 과거 조회 날짜를 일괄 처리 기준으로 사용하지 않는다.
- 정산 확인 건은 기본 선택, 미수금·금액미정은 명시적인 잔금 유지 확인이 필요하다. 단체 공통 미수금은 객실별로 나누지 않는다. 수납·환불·청소 상태는 변경하지 않고 checkedOutAt/arrived만 저장한다.
- 각 퇴실 저장 직전 최신 대상·미수금 검사, 성공·실패/제외 표시, 실패 건만 재선택, 성공 건 누적 표시. 단건 퇴실·결제 흐름도 유지한다.
- 객실별 요금 편집기가 .fld의 86px 라벨 열로 들어가던 문제를 수정했다. 해당 직계 .grr만 전체 열을 차지하며 한글 업무 버튼을 한 글자씩 줄바꿈하지 않는다.

## 요청한 연박·1박 요금 입력 분석 (이번에는 분석과 개선안까지)

SimpleBooking의 총액/박당, 박별 펼침, 타입 요금 제안, 박당 금액 일괄 채움, 날짜별 직접 입력, 총액을 박별 합계로 바꾸기가 동시에 노출되어 같은 가격을 입력하는 방법을 사용자가 먼저 선택·이해해야 한다. 총액과 박별 요금이 별도 상태이므로 총액만 입력하면 카드가 읽는 nightRates가 비어 있을 수 있다.

특히 SimpleBooking.ratesForBooking은 총액 모드에서 직원이 총액을 입력하면(autoActive=false) 1박도 null을 반환한다. 카드의 박별 약정은 저장된 nightRates만 읽어 `요금 미등록`을 표시한다. 즉 총액170,000원은 저장돼도 해당 숙박일의 약정170,000원은 누락되는 구조다.

권장 개편: 객실 타입·기간 선택 후 `매일 같은 요금 / 날짜별 요금 / 총액에서 균등 계산` 세 방식 중 하나만 보여준다. 균일가는 박당×박수와 총액을 즉시 보여주고, 총액 분배는 직원이 명시적으로 선택했을 때만 날짜별 배분·나머지 원 조정 결과를 표시한다. 날짜별 모드는 날짜·요일·요금 표 한 곳에서 입력하고 총액은 합계로 표시한다. 타입 요금은 선택 가능한 초깃값 제공 동작으로 축소한다.

1박·금액확정·객실료170,000원은 해당 날짜170,000원으로 자동 저장하는 것이 타당하다. 추가 항목·얼리/레이트 비용 등이 총액에 포함된 경우 객실료를 분리해야 하며 플랫폼 입금예정액/수납액/환불액을 객실 약정으로 오인하면 안 된다. 기존 데이터는 일괄 보정하지 않는다. 이번 요청의 분석 범위를 지켜 요금 계산/저장 구조 자체는 변경하지 않았다. 별도 요금 입력 개편 시 이 규칙을 공통 저장 경로와 카드에 함께 적용해야 한다.

## 제한

맞교환은 기존 API의 순차 저장+복구 방식이며 여러 사용자의 동시 저장에 대한 DB 단일 트랜잭션은 아니다. 최신 조회로 재검사하지만 다른 사용자가 검사와 저장 사이에 변경하는 극단적인 경쟁까지 클라이언트에서 완전히 원자적으로 막을 수는 없다. 운영 예약에 쓰기 테스트를 하지 않았으며 API에 전달하는 변경 범위는 배치 또는 퇴실 상태로 제한했다.
