# 호토리(HOTORI) 개발·검수 계획 v2

작성일: 2026-10-17 · 현재 결과: 기획·설계 문서 작성. 앱·DB·결제는 아직 구현하지 않음.

기준 문서: [제품 기획](HOTORI-제품기획-v2.md), [기술 설계](HOTORI-기술설계-v2.md).

## 0. 문서 발견과 정책 정리

### 확인한 자료

- 원본 1: `sources/01-원본-개발기획.txt` 전체. 문제·입력 속도·재고·수수료·현장 검증 요구.
- 원본 2: `sources/02-원본-구현명세-v1.txt` 전체. 타입/실물 분리·화면·DB·서버 거래·동시성·권한·검수 요구.
- 2026-10-17 사용자 요청과 추가 답변: 무료/프로, 가격, 3개 플랫폼, 과거와 미래 예약 모두 1/6개월 제한, 객실별 미해결 항목 1/30개.
- 공식 기술 문서: React·Capacitor·PostgreSQL. 공식 판매 정책: Apple·Google. 구체적인 출처는 10절.

### 확인된 사용 가능 수단

- React + TypeScript 웹 UI를 공통 코드로 사용 가능.
- Capacitor로 Android/iOS 플랫폼 프로젝트와 웹 빌드 자산 연결 가능. 공식 설치 순서 후 `npx cap add android`, `npx cap add ios`, `npx cap sync`, `npx cap open android`, `npx cap open ios` 사용 가능. 지금 실행한 명령이 아니다.
- PostgreSQL의 행 잠금, 유일·외래키·겹침 제약, date range, RLS를 근거로 거래·격리 설계 가능.
- 외부 결제 상태를 서버에서 검증하고 호텔별 권한으로 매핑하는 경계를 설계. 결제 제공자 SDK는 아직 선정하지 않았으므로 가상의 SDK 메서드를 제안하지 않음.

### 구현 시작 전 준비

제품 기획 9절의 미결 정책을 추적한다. 웹·서버 프레임워크의 안정 버전, 인증·호스팅·백업 제공자를 고르고 해당 버전 공식 문서를 읽어 잠금 파일과 환경 구성을 고정한다. iOS 빌드 환경과 파일럿 기기를 확인한다. 현재 선택되지 않은 제공자에 대한 API·가격·가용성을 확정한 것으로 쓰지 않는다.

## 1. 호텔·조직·상품 기반

구현: 로그인, 호텔 생성·전환, 소속·역할, 동·타입·객실 설정, 플랜 버전과 서버 정책 판정. 테스트 호텔에 무료·프로 권한을 지정할 수 있게 하되 실결제는 연결하지 않는다. 사용자가 수정하는 일반 설정과 운영자 전용 테스트 권한을 분리한다.

근거/따를 패턴: 기술 설계 2~4·8절, PostgreSQL 공식 Constraints의 복합 유일/외래키 예시와 Row Security Policies의 실제 애플리케이션 역할 검증. 인증 계층은 선정된 제공자의 공식 로그인·세션 예제를 확인한 뒤 적용한다.

검증: 서로 다른 호텔 두 곳과 여러 직원으로 격리, 권한 변경 즉시 반영, A/B동 같은 201호 허용·동 내 중복 거절, 무료 20실/21실, 프로 100실 이상 테스트 구성을 확인한다. 무료 19실에서 두 직원이 동시에 1실씩 추가하면 한 요청만 20번째 실로 성공해야 한다.

금지: 화면에서만 호텔 필터링, 클라이언트의 pro 플래그 신뢰, 유료화 시점에 호텔 ID를 뒤늦게 덧붙이는 설계, 플랜 한도 하드코딩 분산.

완료: 설정 화면에서 입력→서버 저장→재조회가 되고, 다른 호텔·금지 기능은 직접 API로도 접근 불가.

## 2. 예약·재고·입퇴실

구현: 단순 예약 입력과 목록, stay/night 구조, 과거·미래 기간 검사, 변경·전체/부분 취소, 현장 판매, 타입별 재고, 실물 배정, 입퇴실, 서버 거래·멱등성·version 충돌, 실시간 갱신.

근거/따를 패턴: 기술 설계 4~5절, 제품 기획 3.1·4·7절. PostgreSQL Explicit Locking의 `FOR UPDATE`와 일정한 잠금 순서, Range Types의 겹침 방지 패턴을 읽고 적용한다. 복사할 패턴의 버전·마이그레이션 근거를 구현 기록에 남긴다.

검증: 마지막 1실 두 직원 동시 판매, 예약 0건인 날 동시 첫 예약, 다실×연박, 부분 취소, 변경 실패 원복, 월말·윤년 날짜, 과거/미래 한도 경계, 직접 ID 조회와 파일 우회, 재시도 중복, 연속 배정 불가 시 이동 표시.

금지: 화면 숫자만 차감, 취소 시 원거래 삭제, 예약 행이 없는 날 잠금 누락, 배정 때 예약 수량 재차감, 경계 밖 연박 자동 잘라 저장, 범위 밖 데이터를 감사 로그 원문으로 반환.

완료: 핵심 업무를 PC·모바일 웹 UI로 수행하고 정확한 재고·이력·충돌 안내가 확인됨.

## 3. 객실 업무·금액·일일 현황

구현: 동·층 객실 화면, 독립 청소·시설 상태, 날짜별 판매 중지, 인수인계 접수·처리·해결·재열기, 무료1/프로30 한도, 채널·수수료 스냅샷, 일별 매출·결제/환불·예상 및 실제 정산, 외부 채널 수동 확인 안내.

근거/따를 패턴: 제품 기획 3.2~3.3·4~5절, 기술 설계 4~6절. v1의 금액·상태 분리 원칙과 예약 시 수수료 스냅샷을 따르고, 교차 행 한도는 PostgreSQL 잠금 패턴으로 구현한다.

검증: 객실별 한도 독립, 마지막 항목 동시 작성, 해결 뒤 새 항목, 재열기, 한도 중 긴급 고장·판매 중지, 예약 중 객실 고장·수용 부족 표시, 고정 수수료 중복 방지, 원 단위 나머지, 월말 매출·환불·분할 입금.

금지: 메모 저장만으로 자동 판매 중지/재개, 청소 필요를 모든 미래 날짜 중지로 해석, 긴급 고장을 한도 때문에 기록하지 못하게 함, 예상 정산액을 순이익으로 표기, 과거 수수료 자동 재계산.

완료: 프런트가 판매·배정 시 객실 문제를 확인하고, 관리자 일일 금액이 기준 거래와 일치함.

## 4. 프로 기간 통계·출퇴근

구현: 기간별·채널별·타입별 매출·판매율·ADR·RevPAR, 집계 보고서, 팀 출퇴근, 자정 넘김·중복 출근 방지·정정 승인, 호텔별 기능 켜기/끄기. 리포트 과거 범위는 제품 기획 9절의 제안을 확정한 뒤 적용한다.

근거/따를 패턴: 제품 기획 3.2·3.5절과 기술 설계 3·6절. PostgreSQL Constraints의 유일 제약을 열린 근무 중복 방어에 적용하고 근태 명령은 서버 시각으로 기록한다.

지표 정의: 객실박 판매량은 활성 숙박일 수의 합이다. ADR은 객실 숙박 매출/판매 객실박, RevPAR은 객실 숙박 매출/공급 객실박이다. 공급은 가동 객실박에서 판매 중지 객실박을 뺀 값으로 정의해 화면에 표시한다. 분모 0은 비율 0%로 꾸미지 않고 산출 불가로 표시한다. 취소 위약금·다른 추가 매출을 객실 매출 분자에 섞지 않는다.

검증: 무료의 다일 집계 직접 호출 거절, 프로 기간 합계와 일별 합의 일치, 권한 없는 직원의 금액 누출 방지, 출근 두 번 동시 요청, 밤 22시~다음 날 07시, 누락 퇴근 정정, 소속 해제 후 접근, 유료 만료 직전 출근/만료 후 퇴근.

금지: 근태를 무료 팀원 등록과 묶어 모두 잠금, 구독이 직원 권한을 대신함, 단말 시간 신뢰, 정정으로 원본 삭제, 6개월 조회 범위로 1년 전체 보고서를 제공한다고 표시.

완료: 계획한 프로 기능이 실제 화면에서 사용 가능하며 무료 전환 후에도 진행 중 근무를 마칠 수 있음.

## 5. 파일럿 안정화·세 플랫폼 검수

구현: 승인형 CSV 이전과 원본 출력, 오류 복구, 백업·복원, 운영 로그, 웹/PWA 설치, Android/iOS 패키징·로그인·파일 흐름. 기존 웹이 빌드된 뒤 Capacitor 공식 설치·동기화·플랫폼 열기 순서를 적용한다.

근거/따를 패턴: 기술 설계 1·8절, Capacitor Getting Started·Environment Setup·Web·iOS·Android. 플랫폼별 보관·딥링크·파일 연결은 실제 사용하는 공식 플러그인 문서를 먼저 읽고 적용한다. 아직 선택하지 않은 플러그인 메서드를 만들어 호출하지 않는다.

검증: PC 실제 브라우저, Android 실제 기기, iPhone 실제 기기에서 예약·조회·객실 문제·출퇴근·재로그인·뒤로가기·키보드·파일 작업을 수행한다. 네트워크 단절/복귀와 오래된 클라이언트를 확인한다. 복원한 DB에서 호텔·예약·재고·금액·권한·플랜을 대조한다.

금지: 반응형 미리보기만으로 Android/iOS 지원 완료, iOS 빌드 환경 없이 출시 완료, 오프라인 초안을 확정 예약으로 표시, 백업 파일 존재만으로 복구 완료, 실제 고객 데이터를 테스트 DB에 무단 복제.

완료: 호텔이 허용한 파일럿에서 일상 업무를 수행하며 데이터 정합성·출력·복구·실기기 검수가 통과함. 유료 기능은 파일럿 테스트 권한으로 검증 가능하다.

## 6. 유료 상품 출시

구현: 호텔별 가입/구독, 선택한 결제 제공자 어댑터, 검증된 결제 이벤트·대조 작업, 업그레이드·해지·만료·무료 전환, 사용량 표시, 무료 판매 객실 선택, 필요 시 스토어 구매·복원·해지 안내, 고객 지원·자료 반환 절차.

근거/따를 패턴: 제품 기획 7·9절, 기술 설계 7절, Apple/Google 공식 정책. 실제 결제 제공자의 서명 검증·구독 조회·알림·재시도 예제를 먼저 읽고 테스트 환경에 적용한다. 제공자 선정 전 이 단계의 메서드·웹훅 형식을 발명하지 않는다.

검증: 결제 실패·중복·역순 알림, 만료 시각 경합, 잘못된 서명/구매 거절, 호텔 간 구매 이전 차단, 중복 결제 유도 방지, 프로30실→무료20실, 보호 예약과 신규 판매의 재고 충돌, 과거1개월 밖 기록 제한·미처리 예외, 전환 후 내보내기 다운로드 재검사, 재구독 시 보존 자료 복원.

금지: 결제 성공 화면만 믿고 유료 활성화, 외부 이벤트에서 임의 property_id를 신뢰, 앱 내 웹 결제를 정책 검토 없이 기본 확정, 무료 전환으로 예약·객실·근태 원본 삭제, 스토어 심사 통과 보장.

완료: 모든 플랫폼에서 검증된 호텔 이용권이 같은 업무 권한을 부여하고, 실제 선택한 판매 경로의 심사·결제·취소·무료 전환 검수가 통과함.

## 7. 최종 회귀·출시 판정

구현 문서와 선택한 라이브러리 버전의 공식 예제를 대조한다. 실행되지 않는 API, 클라이언트 전용 권한 판정, 범위 밖 조회 우회, 화면 숫자로 오류를 숨기는 코드를 점검한다. 필수 통합·UI·실기기 검수를 실행하고 결과·빌드 식별자·미해결 이슈를 기록한다.

단계 1~6 통과 뒤에도 다음이면 출시를 보류한다: 중복 판매, 금액 오류, 호텔 간 데이터 노출, 제한 우회, 복구 실패, 유료 권한 오판정, 지원 플랫폼 핵심 업무 미완료. 일정이 지났다는 이유로 완료 처리하지 않는다.

## 8. 인수 검수 사례 목록

각 항목은 앞으로 구현 후 실행할 검수다. 현재 통과한 테스트 목록이 아니다.

1. 무료 객실 20개 성공, 21개 실패. 프로 30·100개 설정 성공. ‘무제한’ 부하 보증으로 해석하지 않음.
2. A동201/B동201 성공, 동일 동201 중복 실패. 무료의 신규 동 한도는 제안 정책 확인 후 검수.
3. 과거 하한 날짜 조회 성공, 전날 일반 조회 실패. 직접 ID·검색·감사·파일에도 동일 적용.
4. 미래 상한 전날 숙박·상한일 체크아웃 성공, 상한일 숙박 포함 신규 예약 실패. 월말·윤년 확인.
5. 한도 경계에 걸친 연박에서 허용 구간 밖 금액·이력이 응답에 섞이지 않음.
6. 마지막 객실 동시 예약은 1건만 성공. 빈 날짜 첫 예약도 같은 제어를 받음.
7. 2실2박=4객실박, 1실1박 부분 취소 후 3객실박. 객실 배정해도 점유가 늘지 않음.
8. 날짜/타입 변경 실패 시 기존 점유·금액·이력 유지. 같은 요청 키 재전송은 1건만 생성.
9. 날짜별 재고는 있지만 연속 객실은 없는 연박에 이동 필요 표시와 확인 흐름이 있음.

14. 판매액·수수료·정산·입금·환불 분리. 분할 입금과 취소 수수료가 객실 매출을 왜곡하지 않음.

17. 소유자·프런트·객실관리의 조회 필드/명령 차이. 다른 호텔의 ID·실시간·파일 접근 불가.

19. 프로30실→무료20실에서 기존 미래 예약 유지, 신규 판매는 선택실과 기존 미배정 의무를 함께 검사.
20. 오래된 일반 예약은 기간 제한, 미처리 환불/투숙 등은 필요한 정보만 예외 조회. 완료 후 예외 종료.

## 9. 이후 확장 접수 양식

새 기능마다 다음을 기록한다: 해결할 실제 업무 문제, 사용자/발생 빈도, 현재 처리 방식, 입력과 결과, 무료/프로/후속 상품 구분, 작업 권한, 데이터·보존·개인정보, 기존 예약/재고/금액 영향, 세 플랫폼 화면, 구독 종료 정책, 검수 사례.

청소·시설·인수인계·정산·근태를 계속 확장할 수 있으나 모든 후보를 첫 버전 약속으로 합치지 않는다. 기능을 하나 더할 때 기존 핵심 회귀 검수가 계속 통과해야 한다. 플랜과 기능 코드의 분리로 향후 상위 요금제·추가 모듈을 수용하되 현재는 무료와 프로 두 상품만 정의한다.
